# Users, Groups, Permissions and Service Accounts for DevOps

## Scope

This topic explains Linux identity and access control from a DevOps perspective: Jenkins agents, Ansible, systemd services, EC2 instances, application deployments, secrets, and least-privilege operations.

---

## 1. What is a user in Linux?

A user is an identity used to authenticate and authorize access to system resources.

Important fields are stored in:

```bash
/etc/passwd
/etc/shadow
/etc/group
```

Inspect the current user:

```bash
whoami
id
```

A Linux user has:

- Username
- UID
- Primary group
- Supplementary groups
- Home directory
- Login shell
- Authentication information

---

## 2. What is a UID?

UID means User ID. Linux uses the numeric UID internally for ownership and permission checks.

```bash
id ubuntu
id jenkins
```

Two usernames with the same UID are effectively the same identity from the kernel's perspective.

This matters when:

- Files are copied between servers
- NFS is used
- Containers map host users
- Service accounts are recreated
- Ownership appears as an unknown numeric ID

---

## 3. What is a GID?

GID means Group ID. Groups allow permissions to be assigned to multiple users.

```bash
id
getent group developers
```

Example:

```text
developers:x:2001:jenkins,ubuntu
```

A user can have one primary group and multiple supplementary groups.

---

## 4. What is `/etc/passwd`?

`/etc/passwd` contains account metadata, not normally password hashes.

```bash
cat /etc/passwd
```

Typical format:

```text
username:x:UID:GID:comment:home:shell
```

Example:

```text
jenkins:x:1002:1002:Jenkins:/var/lib/jenkins:/bin/bash
```

Do not edit this file casually. Prefer:

```bash
useradd
usermod
userdel
```

---

## 5. What is `/etc/shadow`?

`/etc/shadow` stores password hashes and password-aging information.

```bash
sudo cat /etc/shadow
```

Access is restricted because it contains sensitive authentication data.

A locked password account may show a marker such as `!` or `*`.

---

## 6. What is a service account?

A service account is a dedicated user used to run an application or agent.

Example:

```bash
sudo useradd \
  --system \
  --home /opt/myapp \
  --shell /usr/sbin/nologin \
  myapp
```

Benefits:

- Least privilege
- Clear ownership
- Better auditing
- Reduced impact of application compromise
- Separation between deployment and runtime identities

---

## 7. Why should applications not run as root?

Root can read, modify, or delete almost everything.

If an application is compromised while running as root, the attacker may gain broad control of the host.

Prefer:

```ini
[Service]
User=myapp
Group=myapp
```

Grant access only to required directories, sockets, devices, and capabilities.

---

## 8. What is the difference between a login user and a service user?

A login user normally has:

- Interactive shell
- Home directory
- Human ownership
- SSH access when configured

A service user normally has:

- No interactive login
- Restricted shell
- Application-specific directories
- No unnecessary sudo privileges

Example restricted shell:

```bash
/usr/sbin/nologin
```

A service user may still need a valid home directory or working directory depending on the application.

---

## 9. How do you create a user?

```bash
sudo useradd -m -s /bin/bash devuser
sudo passwd devuser
```

For a service account:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin myapp
```

Check:

```bash
getent passwd myapp
```

Use configuration management to make account creation repeatable.

---

## 10. How do you modify a user?

```bash
sudo usermod -aG developers ubuntu
sudo usermod -s /bin/bash devuser
sudo usermod -d /home/newhome -m devuser
```

Important:

```bash
usermod -aG developers ubuntu
```

Use `-aG`, not only `-G`, when adding a supplementary group. Without `-a`, existing supplementary groups may be replaced.

---

## 11. How do you remove a user?

```bash
sudo userdel devuser
```

Remove the home directory too:

```bash
sudo userdel -r devuser
```

Before deletion, check:

```bash
pgrep -u devuser
find / -xdev -user devuser -ls
```

A user may own files outside its home directory or run application processes.

---

## 12. What is a group?

A group is a collection of users used for access control.

Create:

```bash
sudo groupadd developers
```

Add a user:

```bash
sudo usermod -aG developers ubuntu
```

View membership:

```bash
groups ubuntu
id ubuntu
```

The user may need to start a new login session before group membership is reflected.

---

## 13. What is the difference between primary and supplementary groups?

The primary group is associated with the user's default file creation group.

Supplementary groups provide additional access.

Check:

```bash
id ubuntu
```

Set primary group:

```bash
sudo usermod -g developers ubuntu
```

Add supplementary group:

```bash
sudo usermod -aG docker ubuntu
```

Changing primary groups can affect newly created files and application behavior.

---

## 14. Explain Linux permissions

Each file has permissions for:

```text
owner | group | others
```

Each class can have:

- `r`: read
- `w`: write
- `x`: execute

Example:

```text
-rwxr-x---
```

Meaning:

- Owner: read, write, execute
- Group: read, execute
- Others: no access

---

## 15. What does `rwx` mean for a directory?

For directories:

- `r`: list directory entries
- `w`: create, delete, or rename entries
- `x`: enter/traverse the directory

A user may be unable to read a file because it lacks `x` permission on a parent directory.

Debug with:

```bash
namei -l /opt/myapp/config/app.env
```

---

## 16. What is numeric permission notation?

Values are:

| Permission | Value |
|---|---:|
| Read | 4 |
| Write | 2 |
| Execute | 1 |

Examples:

```bash
chmod 755 script.sh
chmod 640 app.env
chmod 600 private.key
```

Meaning of `640`:

- Owner: read/write
- Group: read
- Others: no access

---

## 17. What is the difference between `chmod 755` and `chmod 644`?

`755`:

```text
owner: rwx
group: r-x
others: r-x
```

Common for executable scripts and directories.

`644`:

```text
owner: rw-
group: r--
others: r--
```

Common for ordinary readable files.

Do not make secrets or private keys world-readable.

---

## 18. Why is `chmod -R 777` dangerous?

It grants read, write, and execute permissions to everyone.

Risks:

- Any user can modify application files
- Attackers can replace scripts or binaries
- Shared directories become unsafe
- Secrets may be exposed
- Deployment integrity is lost

Correctly identify the required owner, group, and access pattern instead.

---

## 19. What is `chown`?

`chown` changes ownership.

```bash
sudo chown myapp:myapp /opt/myapp/app.jar
sudo chown -R myapp:myapp /opt/myapp/
```

Use recursive ownership changes carefully. Running `chown -R` on a shared directory can break other services.

---

## 20. What is `chgrp`?

`chgrp` changes group ownership.

```bash
sudo chgrp developers /opt/shared
```

A common deployment pattern is:

```bash
sudo chown -R root:developers /opt/shared
sudo chmod -R 2775 /opt/shared
```

The setgid bit can make new files inherit the directory's group.

---

## 21. What is the setgid bit on a directory?

Setgid on a directory causes newly created files and directories to inherit the directory's group.

```bash
sudo chmod 2775 /opt/shared
```

Check:

```bash
ls -ld /opt/shared
```

This is useful for shared deployment directories where Jenkins and application operators need consistent group ownership.

---

## 22. What is the sticky bit?

The sticky bit on a directory restricts deletion of entries to:

- File owner
- Directory owner
- Root

Typical example:

```bash
ls -ld /tmp
```

Usually `/tmp` has permissions similar to:

```text
drwxrwxrwt
```

The `t` is the sticky bit.

---

## 23. What are ACLs?

Access Control Lists provide permissions beyond the basic owner/group/other model.

Check:

```bash
getfacl file.txt
```

Set an ACL:

```bash
setfacl -m u:jenkins:rx /opt/myapp
```

Remove:

```bash
setfacl -x u:jenkins /opt/myapp
```

ACLs are useful when one specific user needs access without changing the main group model.

---

## 24. What is a default ACL?

A default ACL controls permissions inherited by newly created files and directories.

```bash
setfacl -m d:g:developers:rwx /opt/shared
```

Check:

```bash
getfacl /opt/shared
```

Default ACLs are useful for shared build and deployment directories, but they should be documented because they may surprise operators.

---

## 25. How do you troubleshoot “Permission denied”?

Run:

```bash
whoami
id
namei -l /path/to/file
ls -l /path/to/file
getfacl /path/to/file
```

Check:

- Current user
- Group membership
- Parent directory traversal
- File owner and mode
- ACLs
- SELinux/AppArmor
- Read-only filesystem
- NFS identity mapping
- Systemd service user

Do not immediately use `chmod 777`.

---

## 26. How do Jenkins and application users share files safely?

Use a dedicated group:

```bash
sudo groupadd appdeploy
sudo usermod -aG appdeploy jenkins
sudo usermod -aG appdeploy myapp
sudo chown -R root:appdeploy /opt/myapp/releases
sudo chmod -R 2775 /opt/myapp/releases
```

A stronger design is:

- Jenkins writes release directories
- Runtime user reads releases
- Only controlled deployment steps change the `current` symlink
- Persistent data has separate ownership

---

## 27. What is sudoers?

`sudoers` defines who can execute commands with elevated privileges.

Edit safely:

```bash
sudo visudo
```

Example restricted rule:

```text
jenkins ALL=(root) NOPASSWD: /bin/systemctl restart myapp, /bin/systemctl status myapp
```

Avoid giving Jenkins unrestricted root access:

```text
jenkins ALL=(ALL) NOPASSWD: ALL
```

A compromised pipeline could then compromise the entire server.

---

## 28. Why should `sudo` permissions be command-specific?

CI/CD systems execute code from repositories and external dependencies. If the pipeline user has unrestricted sudo, a malicious commit or compromised dependency can execute arbitrary root commands.

Restrict:

- Exact commands
- Exact paths
- Required arguments where practical
- Specific target service
- Specific deployment user

Review sudo rules periodically.

---

## 29. What is SSH key permission best practice?

Private key:

```bash
chmod 600 ~/.ssh/id_ed25519
```

SSH directory:

```bash
chmod 700 ~/.ssh
```

Authorized keys:

```bash
chmod 600 ~/.ssh/authorized_keys
```

Incorrect permissions can cause SSH to reject keys with messages such as:

```text
Permissions are too open
```

---

## 30. What is the difference between authentication and authorization?

Authentication answers:

> Who are you?

Examples:

- Password
- SSH key
- IAM role
- Certificate

Authorization answers:

> What are you allowed to do?

Examples:

- Linux file permissions
- sudoers
- Security groups
- IAM policies
- Kubernetes RBAC

Successful SSH authentication does not automatically mean the user can read or modify application files.

---

## 31. Scenario: Jenkins can deploy files but cannot restart the service

Possible causes:

- Jenkins lacks sudo permission
- Service unit is not accessible
- sudoers rule is incorrect
- Command path differs
- Policy requires a TTY
- Jenkins runs under a different user than expected

Debug:

```bash
sudo -l -U jenkins
sudo -u jenkins id
sudo -u jenkins systemctl status myapp
```

Use a narrow sudoers rule for the required service action.

---

## 32. Scenario: Application starts manually but fails under systemd

Check the service identity:

```bash
systemctl cat myapp
systemctl show myapp -p User -p Group -p WorkingDirectory
```

Test as the service user:

```bash
sudo -u myapp /opt/myapp/current/bin/start
```

Check access:

```bash
namei -l /opt/myapp/current/bin/start
```

The service user may lack access to:

- Application files
- Configuration
- Certificates
- Log directory
- Unix socket
- Mounted data volume

---

## 33. Scenario: A private key works for you but not for Jenkins

Possible causes:

- Key exists only in your home directory
- Jenkins has a different `HOME`
- Permissions reject the key
- SSH known-hosts file is missing
- Jenkins credential was not bound
- Key format is unsupported
- SSH agent is not available

Use Jenkins credentials rather than copying private keys into workspaces.

---

## 34. Scenario: Files created by Jenkins cannot be modified by the application

Check:

```bash
ls -l /opt/myapp/releases
id jenkins
id myapp
```

Possible fixes:

- Shared group
- Setgid directory
- Default ACL
- Correct deployment ownership
- Separate build and runtime directories

Avoid making all files world-writable.

---

- Service accounts

- Primary and supplementary groups
- `rwx` permissions for files and directories
- Numeric permissions
- `chmod`, `chown`, and `chgrp`

- Jenkins/application shared access
- sudoers restrictions
- SSH key permissions

## Key DevOps principle

> Give every automation job and application only the identity and permissions it needs. Least privilege is a deployment reliability and security requirement, not merely a security preference.
