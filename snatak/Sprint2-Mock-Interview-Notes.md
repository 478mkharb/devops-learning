# Git & GitHub

| Question | Answer |
|----------|--------|
| What is a Commit? | A commit is an immutable snapshot of all tracked files in a Git repository at a specific point in time. It stores the project state along with metadata such as the author, timestamp, parent commit, commit message, and a unique SHA identifier. |
| What is a Branch, internally? | A branch is a lightweight, movable pointer to a commit. Instead of creating a separate copy of the repository, Git simply moves the branch reference forward whenever new commits are added to that branch. |
| What is the difference between Git Merge and Git Rebase? | Git Merge combines two branches by creating a merge commit and preserving the complete branch history. Git Rebase rewrites commit history by replaying commits on top of another branch, producing a cleaner and linear commit history. |
| What is Git Stash? | Git Stash temporarily saves uncommitted changes in a stack-like storage without creating a commit. This allows developers to switch branches or perform other tasks before restoring the saved changes when needed. |
| What is Git Cherry-pick? | Git Cherry-pick copies one or more specific commits from one branch and applies them to another branch without merging the entire branch. It is useful for selectively transferring bug fixes or individual features. |
| What is Git Squash? | Git Squash combines multiple commits into a single commit. It is commonly used before merging a feature branch to produce a cleaner, more meaningful commit history that is easier to review and maintain. |
| What is the difference between Git Reset and Git Revert? | Git Reset moves the branch pointer to an earlier commit and can discard commit history or working changes. Git Revert safely creates a new commit that reverses previous changes while preserving the existing project history. |
| What is the difference between Git Fetch, Pull, Clone, and Fork? | Git Fetch downloads remote changes without modifying the local branch. Pull fetches and merges changes. Clone creates a complete local repository. Fork creates a server-side copy of another repository under your own account. |
| What are Client-side Hooks? | Client-side hooks are scripts that run on a developer's local machine before or after Git operations such as commit, merge, or push. They help enforce coding standards, formatting, testing, or commit message validation locally. |
| What are Server-side Hooks? | Server-side hooks execute on the Git server during repository events such as receiving pushes or updating references. They are commonly used to enforce organizational policies, validate commits, control access, and automate deployment workflows. |
| What is the difference between Client-side and Server-side Hooks? | Client-side hooks execute on the developer's local machine and can be bypassed if not enforced. Server-side hooks execute on the Git server, ensuring repository-wide validation and policy enforcement that cannot be skipped by contributors. |
| What are the types of Client-side Git Hooks? | Common client-side Git hooks include **pre-commit**, **prepare-commit-msg**, **commit-msg**, **post-commit**, **pre-rebase**, **post-checkout**, **post-merge**, **pre-push**, and **pre-auto-gc**. They execute on the developer's local machine to validate code, enforce standards, or automate tasks. |
| What are the types of Server-side Git Hooks? | Common server-side Git hooks include **pre-receive**, **update**, **post-receive**, **post-update**, **push-to-checkout**, **proc-receive**, and **reference-transaction**. They execute on the Git server to enforce repository policies, validate pushes, trigger CI/CD pipelines, and automate deployments. |
| What are Branch Protection Rules in GitHub? | Branch Protection Rules safeguard important branches by restricting direct pushes, requiring pull requests, enforcing status checks, mandating code reviews, requiring signed commits, and preventing accidental deletion to maintain code quality and repository integrity. |
| What is the difference between a Monorepo and a Micro Repo? | A Monorepo stores multiple projects in a single repository, simplifying dependency management and coordinated changes. A Micro Repo stores each project separately, providing independent versioning, isolated access control, and simplified repository management. |
| How is Version Control System (VCS) Authentication achieved? | VCS authentication verifies the identity of users accessing repositories. Common methods include Personal Access Tokens (PAT), SSH key authentication, OAuth authentication, GitHub Apps, and enterprise Single Sign-On (SSO) using SAML or OpenID Connect. |
| How is VCS Authorization achieved? | VCS authorization determines the actions an authenticated user can perform. Repository permissions, organization roles, branch protection rules, CODEOWNERS, and access control policies ensure users have only the privileges necessary for their responsibilities. |

# Jenkins

| Question | Answer |
|----------|--------|
| What are the differences between Scripted and Declarative Pipeline? | **1. Conditional Execution:** Declarative provides built-in directives like `when`, `post`, `options`, and `environment`, whereas Scripted requires these to be implemented manually using Groovy. **2. Restart Capability:** Declarative Pipelines support **Restart from Stage** (when enabled), while Scripted Pipelines do not support restarting from an individual stage. **3. Programming Model:** Declarative follows a predefined, structured syntax for readability and validation, whereas Scripted is pure Groovy, offering maximum flexibility for complex and dynamic pipeline logic. |
| What are the types of Jenkins Triggers? | Jenkins supports Manual Trigger, SCM Polling, Webhook Trigger, Cron (Scheduled) Trigger, Upstream Project Trigger, Remote API Trigger, and Build After Other Projects. These triggers automatically or manually initiate pipeline execution. |
| What are Jenkins Parameters? | Jenkins parameters allow users to provide input before a build starts. Common parameter types include String, Boolean, Choice, Password, Text, File, Run, Credentials, and Active Choice parameters for dynamic selections. |
| What are the different Jenkins Credential Types? | Jenkins supports Secret Text, Username with Password, SSH Username with Private Key, Secret File, Certificate, Docker Host Certificate Authentication, Kubernetes Credentials, AWS Credentials, and Vault-based credentials through plugins. |
| How do you connect Jenkins to an EC2 instance in a private subnet? | Jenkins connects through a Bastion Host, VPN, AWS Systems Manager Session Manager (SSM), VPC Peering, Transit Gateway, Direct Connect, or self-hosted agents inside the private subnet that establish outbound connections to Jenkins. |
| What is JNLP and where is a JNLP Agent installed? | **JNLP (Java Network Launch Protocol)** is a mechanism that allows a Jenkins agent to initiate an outbound connection to the Jenkins Controller. A **JNLP (Inbound) Agent** is installed on the **target machine that executes builds**, such as a physical server, virtual machine, EC2 instance, or Kubernetes pod. The agent connects to the Jenkins Controller over the network, making it ideal for systems in private subnets or behind firewalls where inbound connections are restricted. |
| What is JVM Heap Size? | JVM Heap Size is the memory allocated for Java objects during application execution. It is controlled using the -Xms and -Xmx JVM options and directly affects application performance and memory availability. |
| How does JVM Heap Size affect Jenkins? | Insufficient heap causes frequent garbage collection, slow builds, plugin failures, and OutOfMemoryError. Excessive heap may waste memory. Proper sizing ensures stable pipeline execution, plugin performance, and responsive Jenkins operation. |
| What is a Jenkins Agent? | A Jenkins Agent is a machine or container that executes pipeline stages assigned by the Jenkins Controller. Agents distribute workloads, enable parallel execution, and provide isolated build environments for different projects. |
| What is the difference between Controller and Agent? | The Controller manages jobs, schedules builds, and stores configuration, while Agents execute the actual build, test, and deployment tasks. Separating them improves scalability, resource utilization, and security. |
| What is a Jenkins Shared Library? | A Jenkins Shared Library is a reusable collection of Groovy scripts, classes, and resources shared across multiple pipelines. It promotes code reuse, consistency, centralized maintenance, and standardization of CI/CD workflows. |
| What are the src, vars, and resources directories in a Shared Library? | The src directory contains reusable Groovy classes, vars stores globally accessible pipeline functions, and resources contains static files such as templates, configuration files, HTML pages, or other reusable assets. |
| In how many ways can a Shared Library be used in Jenkins? | Shared Libraries can be loaded in three ways: globally configured libraries, folder-level libraries, and dynamically loaded libraries using the library() step. Each approach provides different levels of scope and flexibility. |
| Explain `@Library('shared-library') _` | `@Library('shared-library')` loads a configured Jenkins Shared Library before pipeline execution. The trailing underscore (`_`) is a dummy Groovy statement because the annotation must be attached to a statement. It has no functional purpose and simply enables the library to be loaded, making global functions in `vars/` and classes in `src/` available to the pipeline. |
| What is the difference between Implicit and Explicit Shared Library loading? | Implicit libraries are automatically loaded for every pipeline through Jenkins configuration. Explicit libraries are loaded within the Jenkinsfile using the @Library annotation or the library() step when required. |
| What is a Jenkins Job DSL? | Jenkins Job DSL (Domain-Specific Language) is a Groovy-based scripting framework used to create, update, and manage Jenkins jobs as code. Instead of configuring jobs manually through the Jenkins UI, organizations define jobs in DSL scripts, enabling version control, automation, and consistency. |
| What is a Seed Job? | A Seed Job is a Jenkins job that executes Job DSL scripts to automatically create, update, or delete Jenkins jobs. It serves as the entry point for implementing "Jobs as Code" in Jenkins. |
| What is a DSL Script? | A DSL Script is a Groovy script that defines the configuration of Jenkins resources such as Pipeline jobs, Freestyle jobs, Multibranch Pipelines, folders, views, parameters, triggers, and publishers. |
| What is a Pipeline Job in Job DSL? | A Pipeline Job is created using the `pipelineJob()` DSL block. It defines a Jenkins Pipeline job that executes a Jenkinsfile stored either in the Jenkins job configuration (`cps`) or in a source code repository (`cpsScm`). |
| What is `cpsScm`? | `cpsScm` (Continuation Passing Style - SCM) configures a Pipeline Job to load its Jenkinsfile from a Source Code Management (SCM) repository such as Git, rather than storing the pipeline script inside Jenkins. |
| What is a Multibranch Pipeline? | A Multibranch Pipeline is a Jenkins job type that automatically discovers branches and pull requests in a source code repository. It creates a separate Pipeline job for each branch containing a Jenkinsfile and executes the appropriate pipeline when changes occur. |
| How is a Multibranch Pipeline different from a Pipeline Job? | A Pipeline Job typically builds a single branch specified in its configuration. A Multibranch Pipeline automatically discovers multiple branches and creates separate Pipeline jobs for each branch, allowing independent CI/CD execution. |
| What is `workflowBranchProjectFactory`? | `workflowBranchProjectFactory` is a built-in configuration block provided by the Jenkins Pipeline: Multibranch plugin. It specifies how Jenkins should create Pipeline jobs for discovered branches and where the Jenkinsfile is located using the `scriptPath` property. |
| What is the purpose of `scriptPath`? | `scriptPath` specifies the location of the Jenkinsfile within the source code repository. By default, it is `Jenkinsfile`, but it can point to any relative path such as `ci/Jenkinsfile`. |
| What is the difference between Job DSL and a Multibranch Pipeline? | Job DSL is used to create and manage Jenkins jobs programmatically using Groovy scripts, whereas a Multibranch Pipeline is a Jenkins job type that automatically discovers Git branches and executes the Jenkinsfile for each branch. Job DSL manages Jenkins configuration, while Multibranch Pipeline manages CI/CD execution across branches. |
| What is the difference between Job DSL and a Jenkinsfile? | A Job DSL script defines Jenkins jobs and their configuration, while a Jenkinsfile defines the CI/CD pipeline executed by a Pipeline or Multibranch job. In simple terms, **Job DSL creates Jenkins jobs, whereas a Jenkinsfile defines what those jobs execute.** |
| When should Job DSL be used? | Job DSL is commonly used in enterprise environments where many Jenkins jobs must be created and maintained consistently. It enables version-controlled job definitions, reduces manual configuration, and supports Infrastructure as Code (IaC) practices. |
| What are the different methods of taking backups in Jenkins, and which is the best? | Common backup methods include **manual backup** of the `JENKINS_HOME` directory, **scheduled backups** using shell scripts or cron jobs, the **ThinBackup plugin**, **filesystem snapshots** (EBS/LVM/ZFS), **VM or AMI snapshots**, **container volume backups**, and **Jenkins Configuration as Code (JCasC)** with Git. The **best practice** is to use **scheduled backups of `JENKINS_HOME` combined with JCasC and Git**, supplemented by storage or VM snapshots for disaster recovery. This approach provides reliable recovery of jobs, plugins, configurations, and infrastructure. |
| What is High Availability (HA) in Jenkins? | Jenkins is fundamentally designed as a **single-controller (single-node)** application and does not provide native Active-Active High Availability. For resilience, organizations typically implement **Active-Passive HA**, where a standby controller takes over after a failure using shared storage and backups. Active-Active architectures are generally not recommended because they can lead to configuration and build state inconsistencies. |
| What are Disaster Recovery (DR) strategies for Jenkins? | Jenkins DR includes regular backups of `JENKINS_HOME`, configuration as code, plugin backups, pipeline definitions in Git, external artifact storage, replicated infrastructure, and automated restoration procedures for rapid recovery after failures. |
| What is Pipeline as Code? | Pipeline as Code stores CI/CD pipeline definitions in version control using Jenkinsfiles. This enables versioning, peer reviews, collaboration, rollback capabilities, and consistent pipeline execution across environments. |
| Why is Pipeline as Code preferred over Freestyle Jobs? | Pipeline as Code provides version control, reusability, automation, better maintainability, complex workflow support, code review capabilities, and easier disaster recovery compared to manually configured Freestyle jobs. |
| What is the purpose of Post actions in a Jenkins Pipeline? | Post actions execute after pipeline completion regardless of build status. They perform tasks such as notifications, report publishing, workspace cleanup, artifact archiving, and resource cleanup based on success, failure, or always conditions. |
| What is GitLab? | GitLab is a DevSecOps platform that provides Git-based source code management along with built-in CI/CD, issue tracking, code review, container registry, security scanning, package management, and project management. It enables teams to manage the complete software development lifecycle from a single platform. |
| What is BuildPiper? | BuildPiper is an enterprise Internal Developer Platform (IDP) and CI/CD orchestration tool that simplifies application delivery through reusable pipeline templates, environment management, deployment automation, governance, and integrations with tools such as Jenkins, Kubernetes, GitHub, GitLab, and cloud platforms. |
| Which is better: Jenkins, BuildPiper, or GitLab? | The best tool depends on the use case. **Jenkins** offers maximum flexibility with thousands of plugins and is ideal for highly customized CI/CD pipelines. **GitLab** is best for organizations seeking an integrated DevSecOps platform with built-in SCM and CI/CD. **BuildPiper** is suited for enterprises that require standardized, governed, low-code CI/CD workflows and Internal Developer Platform capabilities. There is no universally "best" tool; the choice depends on organizational requirements. |
| What are Jenkins Monitoring Metrics? | Jenkins Monitoring Metrics provide insights into the health, performance, and availability of the Jenkins controller and agents. Common metrics include **CPU Usage**, **Memory (JVM Heap) Usage**, **Disk Space**, **Disk I/O**, **Build Queue Size**, **Executor Utilization**, **Running/Failed Build Count**, **Build Duration**, **Node/Agent Status**, **HTTP Response Time**, **Thread Count**, **Garbage Collection (GC)**, **Plugin Health**, **Network Usage**, and **Jenkins Uptime**. These metrics are commonly collected using **Prometheus**, **Grafana**, and the **Metrics Plugin**. |

# SonarQube

| Question | Answer |
|----------|--------|
| What is SonarQube? | SonarQube is a static code analysis platform that continuously inspects source code for bugs, vulnerabilities, code smells, duplications, and code coverage. It helps improve software quality by enforcing predefined quality standards during development and CI/CD. |
| What is a Code Smell? | A Code Smell is a maintainability issue that indicates poor coding practices. Although it does not immediately cause failures, it increases technical debt and makes the code harder to understand, modify, and maintain. |
| What is a Bug? | A Bug is a defect in the source code that can produce incorrect results, crashes, exceptions, or unexpected behavior. Bugs affect software reliability and should be fixed to ensure correct application functionality. |
| What is the difference between a Code Smell and a Bug? | A Code Smell affects maintainability without changing application behavior, whereas a Bug causes incorrect functionality or runtime failures. Code Smells increase technical debt, while Bugs directly impact software reliability. |
| What is the difference between Code Quality and Code Coverage? | Code Quality measures maintainability, reliability, security, and coding standards. Code Coverage measures the percentage of source code executed during testing. High coverage alone does not guarantee high-quality or defect-free code. |
| What are SonarQube Rules? | Rules are individual coding standards or security checks that SonarQube applies during analysis. Each rule detects a specific issue such as security vulnerabilities, coding mistakes, performance problems, or maintainability concerns. |
| What is a Quality Profile? | A Quality Profile is a collection of activated rules for a specific programming language. It defines which coding standards and checks are applied during code analysis for projects using that language. |
| What is a Quality Gate? | A Quality Gate is a collection of pass or fail conditions evaluated after code analysis. It determines whether a project meets predefined quality standards before it can proceed through the CI/CD pipeline. |
| What is the difference between Rules, Quality Profiles, and Quality Gates? | Rules define individual checks, Quality Profiles group applicable rules for a language, and Quality Gates evaluate analysis results against configured thresholds to determine whether the project passes quality requirements. |
| How are Maintainability and Reliability achieved in SonarQube? | Maintainability is improved by identifying Code Smells and reducing technical debt. Reliability is improved by detecting Bugs that may cause failures, enabling developers to resolve issues before deployment. |
| What are the types of Sonar Properties files and their use cases? | Common property files include sonar-project.properties for project configuration, global server settings configured in SonarQube, Jenkins pipeline properties, Maven pom.xml properties, and Gradle build.gradle properties for scanner configuration. |
| What is SonarScanner? | SonarScanner is the analysis tool that examines a project's source code and sends the analysis results to a SonarQube or SonarCloud server. It collects source files, executes enabled analysis rules, imports external reports such as code coverage, and uploads the results for quality gate evaluation and dashboard reporting. |
| What are the types of Sonar Scanners? | SonarQube provides **SonarScanner CLI**, **SonarScanner for Maven**, **SonarScanner for Gradle**, **SonarScanner for .NET (formerly MSBuild)**, **SonarScanner for NPM (JavaScript/TypeScript projects via npm package)**, and **SonarScanner for Ant**. The appropriate scanner is selected based on the project's build tool and programming language. |
| What is the H2 Database in SonarQube? | H2 is an embedded database bundled with SonarQube for evaluation and testing purposes. It is not recommended for production because it lacks scalability, reliability, backup capabilities, and high availability features. |
| Why is Elasticsearch bundled with SonarQube? | SonarQube uses Elasticsearch to index source code, issues, metrics, and analysis results. This enables fast searching, efficient querying, responsive dashboards, and quick retrieval of project information during analysis and reporting. |
| What is `vm.max_map_count` and how can it be modified? | `vm.max_map_count` is a Linux kernel parameter that defines the maximum number of memory-mapped areas a process can use. It can be modified **temporarily** using `sudo sysctl -w vm.max_map_count=262144` and **permanently** by adding `vm.max_map_count=262144` to `/etc/sysctl.conf` (or a file under `/etc/sysctl.d/`) and applying it with `sudo sysctl -p` or `sudo sysctl --system`. |
| Why is vm.max_map_count tuning required for SonarQube? | SonarQube embeds Elasticsearch, which relies heavily on memory-mapped files. The default Linux value is usually insufficient, causing Elasticsearch startup failures. Increasing vm.max_map_count ensures stable indexing and search operations. |
| Why doesn't `waitForQualityGate()` simply make one HTTP request? | SonarQube processes analysis asynchronously using its Compute Engine. After `sonar-scanner` uploads the analysis, Jenkins receives only a task ID because the Quality Gate has not yet been calculated. `waitForQualityGate()` repeatedly checks the task status until the Compute Engine finishes processing, then retrieves the final Quality Gate result. |
| What metrics are displayed on the SonarQube Project Dashboard? | The dashboard displays Bugs, Vulnerabilities, Security Hotspots, Code Smells, Code Coverage, Duplicated Code, Technical Debt, Reliability Rating, Security Rating, Maintainability Rating, Lines of Code, and Quality Gate status. |
| What are Security Hotspots in SonarQube? | Security Hotspots are code locations that **may introduce security risks depending on how they are implemented or used**. Unlike vulnerabilities, they are **not automatically considered exploitable**. They require manual review by a developer or security expert to determine whether the code is secure or needs remediation. Examples include **hardcoded credentials**, **weak cryptographic algorithms**, **unsafe HTTP usage**, **SQL query construction**, and **improper file permission handling**. |
| What three criteria are commonly used while creating a Custom Quality Gate? | Custom Quality Gates commonly evaluate Bug count, Vulnerability count, and Code Coverage thresholds. Organizations may also include duplicated code percentage, Security Rating, Reliability Rating, or Maintainability Rating as conditions. |
| What is the default Quality Gate in SonarQube? | The default Quality Gate in SonarQube is **Sonar way**. It follows the **Clean as You Code** approach by evaluating **New Code** using default metrics such as **No new Blocker issues**, **No new Critical issues**, **No new Security Hotspots requiring review**, **Coverage on New Code ≥ 80%**, and **Duplicated Lines on New Code ≤ 3%**. A project must satisfy all configured conditions to pass the Quality Gate. |
| What is High Availability (HA) in SonarQube? | SonarQube High Availability ensures continuous service using multiple application nodes behind a load balancer, a shared external database, and external Elasticsearch support available in the Data Center Edition. |
| What are Disaster Recovery (DR) strategies for SonarQube? | SonarQube DR includes regular database backups, configuration backups, plugin backups, external storage protection, infrastructure replication, and documented recovery procedures to restore services quickly after hardware failures or disasters. |
| What are extensions in SonarQube? | Extensions in SonarQube are plugins that add functionality to the server. They provide support for programming languages, authentication methods, source control integration, reporting, governance, and other features. Examples include **Java Analyzer**, **Python Analyzer**, **JavaScript/TypeScript Analyzer**, **Go Analyzer**, **Git SCM Plugin**, **LDAP Authentication Plugin**, and **SAML Authentication Plugin**. SonarQube loads these extensions during startup to extend its analysis capabilities. |
| What are the important SonarQube configuration files? | The primary SonarQube configuration files are **`sonar.properties`** (server configuration), **`sonar-scanner.properties`** (global SonarScanner CLI configuration), and **`sonar-project.properties`** (project-specific analysis configuration). Build tools such as Maven, Gradle, and .NET can also define Sonar properties in **`pom.xml`**, **`build.gradle`**, or **`.csproj`** instead of using `sonar-project.properties`. |
| What is the purpose of `sonar.properties`, `sonar-scanner.properties`, and `sonar-project.properties`? | **`sonar.properties`** configures the SonarQube server (database, ports, Elasticsearch, authentication, etc.), **`sonar-scanner.properties`** defines global settings for the SonarScanner CLI (server URL, token, defaults), and **`sonar-project.properties`** contains project-specific analysis settings such as project key, source directories, exclusions, and code coverage report paths. |
| What is the purpose of a Project Key in SonarQube? | A **Project Key** is a unique identifier used by SonarQube to distinguish one project from another. It associates analysis results with the correct project, tracks code quality history across multiple scans, and enables CI/CD tools such as Jenkins to continuously update the same project instead of creating a new one. Once assigned, the Project Key should remain stable throughout the project's lifecycle. |

# CI Pipeline Stages

| Question | Answer |
|----------|--------|
| What are the typical CI pipeline stages for a React application? | A React CI pipeline typically includes Checkout Source Code, Install Dependencies (`npm ci`), Syntax Validation, Unit Testing (Jest), Code Coverage (Istanbul), Static Code Analysis (SonarQube), Software Composition Analysis (Trivy/Dependency-Check), Build (`npm run build`), Artifact Archiving, and Build Notification. |
| What are the typical CI pipeline stages for a Python application? | A Python CI pipeline typically includes Checkout Source Code, Create Virtual Environment, Install Dependencies (`pip install`), Syntax Validation, Unit Testing (Pytest), Code Coverage (Coverage.py), Static Code Analysis (SonarQube), Software Composition Analysis (Trivy/Pip Audit), Package Build, Artifact Archiving, and Build Notification. |
| What are the typical CI pipeline stages for a Java application? | A Java CI pipeline typically includes Checkout Source Code, Dependency Resolution (Maven/Gradle), Compilation, Unit Testing (JUnit), Code Coverage (JaCoCo), Static Code Analysis (SonarQube), Software Composition Analysis (OWASP Dependency-Check/Trivy), Package Creation (JAR/WAR), Artifact Archiving, and Build Notification. |
| What are the typical CI pipeline stages for a Go application? | A Go CI pipeline typically includes Checkout Source Code, Dependency Download (`go mod tidy`), Compilation, Unit Testing (`go test`), Code Coverage (`go test -cover`), Static Code Analysis (SonarQube), Software Composition Analysis (Trivy), Binary Generation, Artifact Archiving, and Build Notification. |
| What is the difference between Syntax Validation and Linting? | **Syntax Validation** checks whether source code follows the language's grammar and can be parsed or compiled without syntax errors. **Linting** goes beyond syntax by enforcing coding standards, identifying code smells, unused variables, formatting issues, potential bugs, and best practice violations. For example, a file may pass syntax validation but still fail linting due to poor coding practices. |
| How is code compiled in Go? | Go is a **compiled language**. The Go compiler (`go build`) compiles source code (`.go`) directly into a native machine code executable for the target operating system and architecture. No separate runtime or virtual machine is required to execute the binary. |
| How is code compiled in Java? | Java source code (`.java`) is compiled by the **`javac`** compiler into platform-independent **bytecode (`.class`)**. The **JVM** loads the bytecode, verifies it, and executes it using an interpreter and Just-In-Time (JIT) compiler, enabling platform independence. |
| How is code compiled in Python? | Python is generally considered an interpreted language. Before execution, the Python interpreter compiles the source code (`.py`) into platform-independent **bytecode**. This bytecode may be cached as `.pyc` files in the `__pycache__` directory and is executed by the **Python Virtual Machine (PVM)**. Developers typically run Python programs without performing a separate compilation step. |
| How is code compiled in a React application? | React applications are built using tools such as **Vite**, **Webpack**, or **Create React App**. The build process transpiles modern JavaScript/JSX into browser-compatible JavaScript using **Babel**, bundles modules, optimizes assets, and generates static HTML, CSS, and JavaScript files for deployment. |
| Why is `npm ci` preferred over `npm install` in CI pipelines? | `npm ci` installs dependencies exactly as specified in `package-lock.json`, performs faster clean installations, and ensures reproducible builds, making it the preferred choice for automated CI/CD pipelines. |
| What is a Virtual Environment, and why is it required? | A Virtual Environment is an isolated workspace that maintains its own dependencies, libraries, and package versions for a project. It prevents dependency conflicts between projects, avoids modifying system-wide packages, and ensures reproducible builds across development and CI/CD environments. |
| Which programming languages commonly use Virtual Environments? | Virtual environments are commonly used in **Python** (`venv`, `virtualenv`, `Poetry`), **Node.js** (project-local `node_modules`), **Ruby** (RVM, rbenv, Bundler), and **PHP** (Composer). **Java** and **Go** generally do not require virtual environments because they isolate dependencies through build tools and module systems. |
| Why is a Virtual Environment required for Python but not typically for Java or Go? | Python installs packages globally by default, which can cause version conflicts between projects. A virtual environment isolates project-specific packages. Java uses **Maven/Gradle** to download dependencies per project, while Go uses **Go Modules** (`go.mod`) to manage project-specific dependencies, eliminating the need for separate virtual environments. |
| Why is Code Coverage generated before SonarQube analysis? | SonarQube imports existing coverage reports instead of generating them. Therefore, unit tests and coverage reports must be executed first so SonarQube can include coverage metrics during static code analysis. |
| Why is Static Code Analysis performed before packaging? | Running Static Code Analysis before packaging identifies code quality and security issues early. This prevents packaging and publishing artifacts that fail organizational quality or security standards. |
| Why is Software Composition Analysis performed during the CI pipeline? | Software Composition Analysis identifies vulnerable dependencies, outdated libraries, and license compliance issues before artifacts are built and deployed, reducing software supply chain risks. |
| Why are build artifacts archived in the CI pipeline? | Archiving build artifacts preserves generated binaries, packages, reports, and logs. These artifacts can be downloaded, deployed, audited, or reused in later stages of the CI/CD pipeline. |
| Why are notifications sent at the end of a CI pipeline? | Notifications inform developers about build status, test results, code quality, and security findings, enabling quick response to failures and improving collaboration within the development team. |

# Static Application Security Testing (SAST)

| Question | Answer |
|----------|--------|
| What is Static Application Security Testing (SAST)? | SAST is a white-box security testing technique that analyzes an application's source code, bytecode, or binaries without executing the program. It identifies security vulnerabilities early in the Software Development Lifecycle (SDLC). |
| Why is SAST performed early in the SDLC? | Running SAST during development enables developers to identify and fix security issues before deployment. Early remediation reduces development costs, minimizes security risks, and prevents vulnerabilities from reaching production environments. |
| What vulnerabilities are commonly detected during SAST? | SAST detects SQL Injection, Cross-Site Scripting (XSS), Command Injection, Hardcoded Credentials, Buffer Overflow, Path Traversal, Insecure Cryptography, Null Pointer Dereference, Resource Leaks, and insecure coding practices. |
| Does SAST execute the application during analysis? | No. SAST analyzes source code, bytecode, or compiled binaries without executing the application. It evaluates code structure, data flow, and control flow to identify potential security weaknesses statically. |
| What is Syntax Validation? | Syntax Validation verifies that source code follows the programming language's grammar and syntax rules. It detects missing brackets, invalid statements, incorrect declarations, and other syntax errors before compilation or analysis. |
| Why is Syntax Validation important before Static Code Analysis? | Valid source code enables analysis tools to correctly parse program structure and relationships. Syntax errors can interrupt analysis, generate inaccurate findings, or prevent security and quality tools from completing successfully. |
| What is the difference between SAST and DAST? | SAST analyzes source code without executing the application, identifying vulnerabilities during development. DAST tests a running application from the outside by simulating attacks to discover runtime security vulnerabilities. |
| What is the difference between SAST and Software Composition Analysis (SCA)? | SAST examines custom application source code for security flaws and coding issues. SCA analyzes third-party libraries and dependencies to identify known vulnerabilities, outdated packages, license risks, and supply chain issues. |
| What are the advantages of SAST? | SAST detects vulnerabilities early, integrates with IDEs and CI/CD pipelines, provides precise source-code locations, reduces remediation costs, supports secure coding practices, and improves overall software quality before deployment. |
| What are the limitations of SAST? | SAST may produce false positives, cannot detect runtime vulnerabilities, requires access to source code, and may not identify issues caused by environment configuration or application runtime behavior. |
| Which programming languages are commonly supported by SAST tools? | Most enterprise SAST tools support Java, Python, Go, JavaScript, TypeScript, C, C++, C#, PHP, Ruby, Kotlin, Swift, and many other modern programming languages used in enterprise development. |
| How is SAST integrated into a CI/CD pipeline? | SAST tools execute automatically during code commits or build stages. The pipeline analyzes source code, generates security reports, and can fail the build if vulnerabilities exceed predefined security or quality thresholds. |
| Name some commonly used SAST tools. | Popular SAST tools include SonarQube, Semgrep, Checkmarx, Fortify Static Code Analyzer, Veracode Static Analysis, GitHub CodeQL, Coverity, PMD, SpotBugs, and ESLint for language-specific analysis. |

# Software Composition Analysis (SCA)

| Question | Answer |
|----------|--------|
| What is Software Composition Analysis (SCA)? | Software Composition Analysis (SCA) identifies and analyzes open-source libraries, third-party dependencies, and their transitive dependencies used in an application. It detects known vulnerabilities, license risks, and outdated components throughout the software supply chain. |
| Why is SCA important? | Modern applications rely heavily on open-source libraries. SCA helps organizations identify vulnerable dependencies, enforce license compliance, reduce supply chain risks, and maintain secure, up-to-date software components throughout the development lifecycle. |
| What is the difference between SAST and SCA? | SAST analyzes custom application source code for coding flaws and security vulnerabilities. SCA analyzes third-party dependencies to detect known CVEs, outdated packages, license compliance issues, and software supply chain risks. |
| What is a dependency in SCA? | A dependency is an external library, framework, or package required by an application. Dependencies may be direct, explicitly added by developers, or transitive, automatically included through other libraries. |
| What are transitive dependencies? | Transitive dependencies are libraries automatically installed because another dependency requires them. Although developers may not reference them directly, they can still introduce vulnerabilities and license compliance risks into the application. |
| What vulnerabilities does SCA detect? | SCA detects known Common Vulnerabilities and Exposures (CVEs), outdated libraries, unsupported components, malicious packages, vulnerable transitive dependencies, and software supply chain risks affecting third-party dependencies. |
| What are Open Source Licenses? | Open Source Licenses define how software can be used, modified, and distributed. They specify user rights, obligations, attribution requirements, and redistribution conditions for open-source software components. |
| What are the common types of Open Source Licenses? | Common licenses include MIT, Apache 2.0, BSD, GPL, LGPL, MPL, Eclipse Public License (EPL), and Creative Commons licenses. They differ mainly in redistribution requirements, copyleft obligations, and patent protections. |
| What is the difference between Permissive and Copyleft Licenses? | Permissive licenses, such as MIT and Apache 2.0, allow proprietary modifications with minimal restrictions. Copyleft licenses, such as GPL, require derivative works to be distributed under the same license terms. |
| What is SBOM? | A Software Bill of Materials (SBOM) is a machine-readable inventory of all software components, libraries, versions, suppliers, and dependencies included in an application. It improves transparency, vulnerability management, and regulatory compliance. |
| Why is SBOM important? | SBOM enables organizations to quickly identify affected software components when new vulnerabilities are disclosed. It improves software supply chain visibility, simplifies compliance audits, and accelerates incident response during security events. |
| What are the common SBOM standards? | The two widely adopted SBOM standards are SPDX (Software Package Data Exchange) and CycloneDX. Both provide standardized formats for documenting software components, dependencies, licenses, and vulnerability-related metadata. |
| What are License Scanning Tools? | License scanning tools analyze software dependencies to identify license types, detect compliance violations, and ensure that open-source components meet organizational and legal requirements before software distribution. |
| Name some commonly used SCA and License Scanning tools. | Popular tools include Trivy, OWASP Dependency-Check, Syft, Grype, Snyk, Mend (WhiteSource), Black Duck, FOSSA, GitHub Dependabot, and JFrog Xray for dependency, vulnerability, and license analysis. |
| What is Trivy? | Trivy is an open-source security scanner that identifies vulnerabilities, misconfigurations, secrets, software licenses, and SBOM information in containers, operating systems, source code repositories, and Infrastructure as Code configurations. |
| What is OWASP Dependency-Check? | OWASP Dependency-Check analyzes project dependencies and matches them against the National Vulnerability Database (NVD) to identify publicly known CVEs affecting third-party libraries used by an application. |
| What is GitHub Dependabot? | Dependabot continuously monitors project dependencies, detects newly disclosed vulnerabilities, and automatically creates pull requests to upgrade affected packages, helping developers keep software dependencies secure and current. |
| How is SCA integrated into a CI/CD pipeline? | SCA tools execute during build or dependency installation stages, analyze project manifests and lock files, generate vulnerability reports, and optionally fail the pipeline when critical vulnerabilities or prohibited licenses are detected. |
| Can SCA detect vulnerabilities in custom source code? | No. SCA focuses on third-party components and open-source dependencies. Vulnerabilities within custom application code are identified using Static Application Security Testing (SAST) or Dynamic Application Security Testing (DAST). |
| What are the benefits of integrating SCA into DevSecOps? | Integrating SCA into DevSecOps enables continuous dependency monitoring, faster vulnerability remediation, automated license compliance, improved software supply chain security, and consistent enforcement of organizational security policies across development pipelines. |

# Unit Testing & Code Coverage

| What is Unit Testing? | Unit Testing is the process of testing individual functions, methods, or classes in isolation to verify they behave as expected. It helps detect defects early and ensures each software component functions correctly. |

High coverage does not necessarily imply high-quality or defect-free software. |

| What is the de facto Unit Testing framework for Python? | Pytest is the most widely used Python testing framework. It provides simple test syntax, fixtures, parameterized testing, plugin support, and integrates well with coverage tools and CI/CD pipelines. |
| What is the de facto Code Coverage tool for Python? | Coverage.py is the de facto code coverage tool for Python. It measures executed code during test runs and works seamlessly with Pytest to generate HTML, XML, and terminal coverage reports. |

| Question | Answer |
|----------|--------|
| What is Maven? | Maven is a build automation and dependency management tool for Java projects. It standardizes project structure, manages dependencies, executes build lifecycles, runs tests, packages applications, and integrates with CI/CD tools such as Jenkins and SonarQube. |
| What is JDK? | The Java Development Kit (JDK) is the complete Java development environment. It includes the JVM, JRE, Java compiler (`javac`), debugger, and other development tools required to build, compile, and package Java applications. |
| What is JRE? | The Java Runtime Environment (JRE) provides the libraries and JVM required to run Java applications. It does not include development tools such as the Java compiler (`javac`). |
| What is JVM? | The Java Virtual Machine (JVM) is the runtime engine that executes Java bytecode. It provides platform independence by allowing compiled Java programs to run on any operating system with a compatible JVM. |
| What is `javac`? | `javac` is the Java compiler included in the JDK. It converts human-readable Java source files (`.java`) into platform-independent bytecode (`.class`) that can be executed by the JVM. |
| How is a Java program compiled and executed? | A Java source file (`.java`) is compiled by `javac` into bytecode (`.class`). The JVM loads the bytecode, verifies it, and executes it using an interpreter and Just-In-Time (JIT) compiler for improved performance. |
| What is Bytecode? | Bytecode is the platform-independent intermediate code generated by the Java compiler (`javac`). It is stored in `.class` files and executed by the JVM on any supported operating system. |
| What is the difference between JDK, JRE, and JVM? | The **JDK** provides development tools for building Java applications, the **JRE** provides the runtime environment to execute them, and the **JVM** is the engine within the JRE that executes Java bytecode. |
| What is the Maven Build Lifecycle? | Maven follows a predefined build lifecycle consisting of phases that automate project compilation, testing, packaging, verification, installation, and deployment. Executing a phase automatically runs all preceding phases in order. |
| What are the phases of the Maven Default Lifecycle? | The primary phases are **validate**, **compile**, **test**, **package**, **verify**, **install**, and **deploy**. Maven executes these phases sequentially during a build. |
| What does the `validate` phase do? | The `validate` phase verifies that the project structure and configuration are correct, ensuring all required information is available before the build proceeds. |
| What does the `compile` phase do? | The `compile` phase compiles Java source code from the `src/main/java` directory into bytecode (`.class` files) using the Java compiler (`javac`). |
| What does the `test` phase do? | The `test` phase executes unit tests using frameworks such as JUnit or TestNG without packaging or deploying the application. |
| What does the `package` phase do? | The `package` phase packages the compiled application into a distributable format such as a JAR or WAR file based on the project's packaging type. |
| What does the `verify` phase do? | The `verify` phase performs additional quality checks, integration with plugins, and validation to ensure the packaged artifact satisfies all quality requirements before installation or deployment. |
| What does the `install` phase do? | The `install` phase copies the generated artifact into the local Maven repository (`~/.m2/repository`) so it can be used as a dependency by other local projects. |
| What does the `deploy` phase do? | The `deploy` phase uploads the packaged artifact to a remote Maven repository such as Nexus or Artifactory, making it available for other developers and deployment pipelines. |
| What is `pom.xml`? | `pom.xml` (Project Object Model) is Maven's primary configuration file. It defines project metadata, dependencies, plugins, repositories, build settings, and project version information. |
| What is the Maven Local Repository? | The local repository is the directory (`~/.m2/repository`) where Maven stores downloaded dependencies and locally built artifacts to avoid repeated downloads. |
| What is the Maven Central Repository? | Maven Central is the default public repository from which Maven downloads open-source dependencies when they are not available in the local repository. |
| What is Dependency Management in Maven? | Dependency management allows Maven to automatically download, resolve, and manage project dependencies along with their transitive dependencies using the declarations in `pom.xml`. |
| What are Transitive Dependencies in Maven? | Transitive dependencies are libraries automatically downloaded because another dependency requires them. Maven resolves these dependencies recursively to build the complete dependency tree. |
| How does Maven versioning work? | Maven versions generally follow the format **MAJOR.MINOR.PATCH** (Semantic Versioning). **MAJOR** indicates incompatible changes, **MINOR** introduces backward-compatible features, and **PATCH** contains backward-compatible bug fixes. Development versions often use the **-SNAPSHOT** suffix. |
| What is a SNAPSHOT version in Maven? | A SNAPSHOT version represents a development build that may change over time. Maven checks remote repositories for updated SNAPSHOT artifacts during builds, unlike release versions, which are immutable. |
| What is a Release version in Maven? | A Release version is a stable, immutable artifact published for production use. Once released, its contents should never change, ensuring reproducible builds across environments. |

# OWASP ZAP (Dynamic Application Security Testing - DAST)

| Question | Answer |
|----------|--------|
| What is OWASP ZAP? | OWASP ZAP (Zed Attack Proxy) is an open-source Dynamic Application Security Testing (DAST) tool that identifies security vulnerabilities in running web applications by simulating real-world attacks without accessing the source code. |
| What is Dynamic Application Security Testing (DAST)? | DAST analyzes a running application from the outside by sending HTTP requests and evaluating responses. It detects runtime vulnerabilities without requiring access to the application's source code or internal implementation. |
| What is the difference between SAST and DAST? | SAST analyzes source code without executing the application, identifying coding flaws early. DAST evaluates a running application from an attacker's perspective to identify runtime vulnerabilities and security misconfigurations. |
| How does OWASP ZAP work? | OWASP ZAP acts as an intercepting proxy between the browser and application. It captures HTTP/HTTPS traffic, crawls application pages, performs active security scans, and generates detailed vulnerability reports for identified security issues. |
| How does OWASP ZAP discover application pages? | ZAP discovers pages using traditional crawling (Spider), AJAX Spider for JavaScript-heavy applications, manually explored pages, imported URLs, API definitions, and authenticated sessions configured by the user. |
| How does OWASP ZAP discover authenticated pages? | ZAP requires a configured authentication context with login credentials, authentication method, session management, and user definitions. Without authentication, it can crawl only publicly accessible pages and resources. |
| What is the Spider in OWASP ZAP? | The Spider automatically crawls traditional web applications by following hyperlinks, forms, and discovered resources. It builds a site map that becomes the foundation for subsequent security scanning activities. |
| What is AJAX Spider? | AJAX Spider is designed for modern JavaScript-based applications. It uses a browser engine to execute client-side scripts, allowing ZAP to discover dynamically generated pages and Single Page Application (SPA) content. |
| What is Passive Scanning? | Passive Scanning analyzes HTTP requests and responses without modifying traffic or sending malicious payloads. It identifies security issues such as missing HTTP headers, information disclosure, and insecure cookie configurations. |
| What is Active Scanning? | Active Scanning sends crafted attack payloads to application endpoints to identify exploitable vulnerabilities such as SQL Injection, Cross-Site Scripting (XSS), Command Injection, and other runtime security weaknesses. |
| What vulnerabilities can OWASP ZAP detect? | ZAP detects SQL Injection, Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF), Command Injection, Directory Traversal, Server Misconfigurations, Missing Security Headers, Weak Authentication, and Session Management issues. |
| What is a Context in OWASP ZAP? | A Context defines the scope of a security assessment by specifying target URLs, authentication methods, users, session handling, and inclusion or exclusion rules for the application being tested. |
| What is Forced Browse in OWASP ZAP? | Forced Browse attempts to discover hidden files and directories by testing common filenames and paths. It helps identify unintentionally exposed resources that are not linked within the application. |
| What reports can OWASP ZAP generate? | OWASP ZAP generates security assessment reports in HTML, XML, JSON, Markdown, and SARIF formats. These reports include detected vulnerabilities, affected URLs, severity levels, evidence, and remediation recommendations. |
| How is OWASP ZAP integrated into a CI/CD pipeline? | ZAP can run automatically during CI/CD using Docker containers, Jenkins, GitHub Actions, GitLab CI, Azure DevOps, or command-line scripts to scan deployed applications before production release. |
| What are the advantages of OWASP ZAP? | OWASP ZAP is free, open source, easy to automate, supports authenticated scanning, integrates with CI/CD pipelines, provides REST APIs, and detects a broad range of web application security vulnerabilities. |
| What are the limitations of OWASP ZAP? | ZAP requires a running application, cannot analyze source code, may generate false positives, depends on proper authentication configuration, and cannot detect vulnerabilities hidden within inaccessible application functionality. |

# SSL/TLS & Cryptography

| Question | Answer |
|----------|--------|
| What is SSL? | Secure Sockets Layer (SSL) is a cryptographic protocol designed to secure communication between clients and servers. Although deprecated, the term SSL is still commonly used to refer to modern TLS-based encrypted connections. |
| What is TLS? | Transport Layer Security (TLS) is the successor to SSL. It provides encryption, authentication, and data integrity for communication over networks, protecting sensitive information from interception and tampering. |
| What is the difference between SSL and TLS? | SSL is an older protocol with known security weaknesses and is no longer recommended. TLS is the modern, more secure protocol that supports stronger encryption algorithms, improved authentication, and enhanced protection against attacks. |
| What is an SSL/TLS Certificate? | An SSL/TLS certificate is a digitally signed document that binds a public key to a domain or organization. It verifies the server's identity and enables encrypted communication between clients and servers. |
| Why is an SSL/TLS certificate required? | SSL/TLS certificates establish encrypted communication, verify server identity, prevent eavesdropping, protect sensitive information, and build user trust by enabling secure HTTPS connections. |
| What is Symmetric Encryption? | Symmetric encryption uses a single shared key for both encryption and decryption. It is computationally efficient and is primarily used for encrypting application data after a secure connection has been established. |
| What is Asymmetric Encryption? | Asymmetric encryption uses a pair of mathematically related keys: a public key for encryption and a private key for decryption. It enables secure key exchange, digital signatures, and identity verification. |
| What is the difference between Symmetric and Asymmetric Encryption? | Symmetric encryption uses one shared key and offers high performance for bulk data encryption. Asymmetric encryption uses public and private keys, making it suitable for secure key exchange and authentication despite being computationally slower. |
| How does SSL/TLS use both Symmetric and Asymmetric Encryption? | During the TLS handshake, asymmetric encryption securely exchanges or negotiates a session key. Afterward, symmetric encryption protects all application data because it is significantly faster and more efficient. |
| What is a Public Key? | A public key is openly distributed and used to encrypt data or verify digital signatures. It can be safely shared without compromising the security of the corresponding private key. |
| What is a Private Key? | A private key is a confidential cryptographic key used to decrypt encrypted data and generate digital signatures. It must remain secret because anyone possessing it can impersonate the certificate owner. |
| What is a Certificate Authority (CA)? | A Certificate Authority is a trusted organization that verifies domain or organizational ownership and digitally signs SSL/TLS certificates, enabling clients to trust the identity of secure servers. |
| What is a Self-Signed Certificate? | A self-signed certificate is signed by its own creator rather than a trusted Certificate Authority. It is suitable for development and testing but is generally not trusted by web browsers in production. |
| What is HTTPS? | HTTPS is the secure version of HTTP that uses TLS to encrypt communication between clients and servers. It provides confidentiality, integrity, and authentication for web traffic transmitted over the internet. |
| What is the TLS Handshake? | The TLS handshake establishes a secure connection by negotiating protocol versions, selecting encryption algorithms, authenticating the server using certificates, exchanging session keys, and verifying secure communication parameters. |
| What are the common SSL/TLS certificate types? | Common certificate types include Domain Validated (DV), Organization Validated (OV), Extended Validation (EV), Wildcard Certificates, Multi-Domain (SAN) Certificates, and Code Signing Certificates for software publishers. |
| Which tools are commonly used to generate SSL/TLS certificates? | Common tools include OpenSSL, CFSSL, Easy-RSA, Java Keytool, Let's Encrypt Certbot, HashiCorp Vault PKI, Microsoft Certificate Services, and AWS Certificate Manager (ACM). |
| What is OpenSSL? | OpenSSL is an open-source cryptographic toolkit used to generate private keys, create Certificate Signing Requests (CSRs), issue certificates, manage cryptographic operations, and troubleshoot SSL/TLS connections. |
| What is a Certificate Signing Request (CSR)? | A CSR is a file generated by a server containing its public key and identity information. It is submitted to a Certificate Authority to request the issuance of a trusted SSL/TLS certificate. |
| What is Let's Encrypt? | Let's Encrypt is a free, automated Certificate Authority that issues trusted SSL/TLS certificates. It integrates with tools such as Certbot to automate certificate issuance, installation, and renewal. |
| What is Certbot? | Certbot is an open-source client developed by the Electronic Frontier Foundation (EFF). It automates requesting, installing, configuring, and renewing Let's Encrypt SSL/TLS certificates on supported web servers. |
| What is AWS Certificate Manager (ACM)? | AWS Certificate Manager is a managed AWS service that provisions, deploys, renews, and manages public and private SSL/TLS certificates for AWS services such as Elastic Load Balancers, CloudFront, and API Gateway. |
| How can you verify an SSL/TLS certificate? | SSL/TLS certificates can be verified using browser certificate information, OpenSSL commands, online SSL testing tools, or by checking certificate validity, issuer, expiration date, and hostname matching. |
| What are the benefits of using SSL/TLS? | SSL/TLS protects data confidentiality, ensures data integrity, authenticates servers, prevents man-in-the-middle attacks, improves customer trust, and is required for secure modern web applications and regulatory compliance. |

Immutable deployments provide better consistency, easier rollback, and more predictable production environments. |

| Which infrastructure model is commonly used for Staging? | Staging environments generally use Immutable Infrastructure to closely match production. This ensures deployment validation occurs on infrastructure that is identical to the production environment before release. |

| What is Authentication? | Authentication is the process of verifying the identity of a user, application, or service before granting access to a system. It answers the question, "Who are you?" |
| What is Authorization? | Authorization determines what an authenticated user or service is permitted to access or perform. It answers the question, "What are you allowed to do?" |
| What is the difference between Authentication and Authorization? | Authentication verifies identity using credentials such as passwords, tokens, or certificates. Authorization evaluates permissions and access policies to determine which resources and actions are allowed after successful authentication. |
| How is VCS Authentication achieved? | Version Control Systems authenticate users using HTTPS with Personal Access Tokens (PAT), SSH key authentication, OAuth, GitHub Apps, or enterprise Single Sign-On (SSO) integrated with identity providers. |
| How is VCS Authorization achieved? | VCS authorization is implemented through repository permissions, organization roles, branch protection rules, CODEOWNERS, team memberships, and fine-grained access controls that determine user privileges after authentication. |
| What is Personal Access Token (PAT)? | A Personal Access Token is a secure alternative to passwords for HTTPS-based Git authentication. It contains configurable scopes that limit access to specific repositories or operations. |
| What is SSH Key Authentication? | SSH authentication uses a public-private key pair to securely verify a user's identity without transmitting passwords. The public key is stored on the Git server, while the private key remains with the user. |
| What is OAuth Authentication? | OAuth enables users to authenticate using trusted identity providers without sharing passwords directly with applications. It issues access tokens that applications use to access approved resources securely. |
| What is Single Sign-On (SSO)? | Single Sign-On allows users to authenticate once through a centralized identity provider and securely access multiple applications without signing in separately to each service. |

# License Scanning

| Question | Answer |
|----------|--------|
| What is License Scanning? | License Scanning is the process of identifying the open-source licenses associated with third-party dependencies used in an application. It helps organizations detect license compliance issues, enforce organizational policies, and prevent the use of licenses that may impose legal or distribution restrictions. |
| What are the types of Open Source Licenses? | Open Source Licenses are broadly classified into **Permissive** and **Copyleft** licenses. **Permissive licenses** (e.g., MIT, Apache 2.0, BSD) allow software to be modified and distributed with minimal restrictions. **Copyleft licenses** (e.g., GPL, LGPL, MPL) require derivative works to preserve the original license under specified conditions. |
| Where are dependency licenses stored? | Dependency licenses are typically stored within the dependency package itself as a **`LICENSE`**, **`LICENSE.txt`**, or **`COPYING`** file, and are often referenced in the package metadata (e.g., **`package.json`** for npm, **`pom.xml`** for Maven, **`METADATA`** for Python packages, and **`go.mod`** or module metadata for Go). License scanning tools read these files and metadata to determine the applicable license. |

# Cred Scanning

| Question | Answer |
|----------|--------|
| What is Credential (Secret) Scanning? | Credential (Secret) Scanning is the process of detecting sensitive information such as passwords, API keys, access tokens, SSH keys, private keys, certificates, and cloud credentials that have been accidentally committed to source code, configuration files, or Git repositories. It helps prevent unauthorized access and security breaches. |
| What are the commonly used tools for Credential (Secret) Scanning? | Common credential scanning tools include **Gitleaks**, **GitHub Secret Scanning**, **TruffleHog**, **GitGuardian**, **Detect Secrets (Yelp)**, **Talisman**, **Trivy (Secrets Scanner)**, **SpectralOps**, and **Checkmarx Secrets Detection**. These tools identify exposed secrets before code reaches production. |
