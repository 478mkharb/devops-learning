# Maven

### Q1. What is Apache Maven?

**Answer:** Apache Maven is a build automation and dependency-management tool primarily used for Java and JVM-based projects. It uses a declarative `pom.xml` file to define project metadata, dependencies, plugins, build configuration, and lifecycle behavior.

---

### Q2. What is `pom.xml`?

**Answer:** `pom.xml` stands for **Project Object Model**. It is Maven's primary project configuration file and defines project metadata, dependencies, plugins, repositories, profiles, and build configuration.

---

### Q3. What are Maven coordinates?

**Answer:** Maven coordinates identify an artifact using values such as `groupId`, `artifactId`, and `version`.

| Coordinate | Purpose |
|---|---|
| `groupId` | Identifies the organization or logical group |
| `artifactId` | Identifies the project or artifact |
| `version` | Identifies the artifact version |
| `packaging` | Defines the artifact type, such as `jar` or `war` |

Example:

```xml
<groupId>com.company</groupId>
<artifactId>order-service</artifactId>
<version>1.0.0</version>
```

---

### Q4. What is the Maven `.m2` directory?

**Answer:** `.m2` is Maven's user-level configuration and local repository directory. The default location is:

```text
~/.m2/
```

The `repository/` subdirectory stores downloaded dependencies, plugins, and metadata.

```text
.m2/
├── repository/
│   └── groupId/artifactId/version/
└── settings.xml
```

`settings.xml` is optional and is used for user-specific Maven configuration such as mirrors, credentials, profiles, and repository settings.

---

### Q5. When is the Maven local repository created?

**Answer:** Maven creates and populates the local repository as required when Maven needs to resolve artifacts or plugins. A command such as `mvn compile` on a new project commonly causes Maven to create `~/.m2/repository` and download required artifacts.

`mvn -version` only displays Maven and Java information and should not be relied upon as a command that creates the local repository.

---

### Q6. Why is the Maven local repository important in CI/CD?

**Answer:** The Maven local repository acts as a dependency and plugin cache. Persisting or caching `~/.m2/repository` between CI builds can reduce download time and dependency traffic to remote repositories.

---

### Q7. What are Maven lifecycles?

**Answer:** Maven provides predefined lifecycles that organize build activities into ordered phases. The three main Maven lifecycles are **default**, **clean**, and **site**.

| Lifecycle | Purpose |
|---|---|
| **default** | Build, test, package, verify, install, and deploy |
| **clean** | Remove files generated by previous builds |
| **site** | Generate project documentation and reports |

---

### Q8. What is the Maven default lifecycle?

**Answer:** The default lifecycle is the main lifecycle used to build and deliver a Maven project.

```text
validate
   ↓
compile
   ↓
test
   ↓
package
   ↓
verify
   ↓
install
   ↓
deploy
```

There are additional phases between these commonly used phases.

---

### Q9. What are the phases of the Maven default lifecycle?

**Answer:** The default lifecycle contains the following phases in order:

| Phase | Purpose |
|---|---|
| `validate` | Validate the project |
| `initialize` | Initialize build state |
| `generate-sources` | Generate source code if configured |
| `process-sources` | Process source code |
| `generate-resources` | Generate resources |
| `process-resources` | Process/copy resources |
| `compile` | Compile main source code |
| `process-classes` | Post-process compiled classes |
| `generate-test-sources` | Generate test source code |
| `process-test-sources` | Process test source code |
| `generate-test-resources` | Generate test resources |
| `process-test-resources` | Process test resources |
| `test-compile` | Compile test source code |
| `process-test-classes` | Post-process test classes |
| `test` | Run unit tests |
| `prepare-package` | Prepare files before packaging |
| `package` | Create the project artifact |
| `pre-integration-test` | Prepare for integration tests |
| `integration-test` | Run integration tests |
| `post-integration-test` | Clean up after integration tests |
| `verify` | Verify the package and build checks |
| `install` | Install the artifact into the local repository |
| `deploy` | Publish the artifact to a remote repository |

---

### Q10. What does the `validate` phase do?

**Answer:** `validate` is an early phase of the default lifecycle. It checks that the project is correctly structured and that required information is available before later build phases execute.

It does not compile application source code.

---

### Q11. What does the `compile` phase do?

**Answer:** The `compile` phase compiles the project's main source code into bytecode. For a typical Java project, `.java` files are compiled into `.class` files under `target/classes`.

---

### Q12. What does the `test` phase do?

**Answer:** The `test` phase executes unit tests against the compiled test code. Maven commonly uses the **Maven Surefire Plugin** to execute unit tests.

---

### Q13. What does the `package` phase do?

**Answer:** The `package` phase packages the compiled application into the artifact type specified by the project, such as a JAR or WAR.

Example:

```text
target/
└── order-service-1.0.0.jar
```

---

### Q14. What does the `verify` phase do?

**Answer:** The `verify` phase runs checks that verify the project package meets the required quality or integration conditions. Plugins can bind additional checks to this phase.

---

### Q15. What does the `install` phase do?

**Answer:** The `install` phase installs the project's packaged artifact and associated metadata into the local Maven repository, normally under `~/.m2/repository`.

---

### Q16. What does the `deploy` phase do?

**Answer:** The `deploy` phase publishes the project's artifact and metadata to a configured remote Maven repository, such as Nexus or Artifactory.

---

### Q17. What is the difference between `validate` and `verify`?

**Answer:** `validate` is an early project-validation phase, while `verify` occurs near the end of the default lifecycle and verifies the built package and associated checks.

| Aspect | `validate` | `verify` |
|---|---|---|
| Position | Early | Near the end |
| Main focus | Project/build configuration validity | Verification of the built package |
| Compilation already completed | No | Yes, when reached normally |
| Typical role | Early build validation | Final verification before install/deploy |

---

### Q18. What happens when you run `mvn package`?

**Answer:** Maven executes the applicable phases from the beginning of the default lifecycle through `package`.

```text
validate
  ↓
initialize
  ↓
...
compile
  ↓
test
  ↓
package
```

Therefore, `mvn package` normally compiles the application, runs tests, and then creates the package.

---

### Q19. Does Maven execute previous lifecycle phases automatically?

**Answer:** Yes. When you invoke a lifecycle phase, Maven executes that phase and all earlier phases in the same lifecycle.

For example:

```bash
mvn test
```

executes the lifecycle through `test`.

```bash
mvn install
```

executes the lifecycle through `install`.

---

### Q20. What is the difference between `mvn clean`, `mvn package`, and `mvn clean package`?

**Answer:** These commands perform different operations.

| Command | Result |
|---|---|
| `mvn clean` | Executes the clean lifecycle and removes build output such as `target/` |
| `mvn package` | Builds and packages the project through `package` |
| `mvn clean package` | Cleans the previous build and then performs a fresh package build |

---

### Q21. What is the Maven clean lifecycle?

**Answer:** The clean lifecycle removes files generated by previous Maven builds.

```text
pre-clean → clean → post-clean
```

The `clean` phase normally removes the project's `target/` directory.

---

### Q22. What is the Maven site lifecycle?

**Answer:** The site lifecycle generates project documentation and reports.

```text
pre-site → site → post-site → site-deploy
```

It is separate from the default lifecycle used to build application artifacts.

---

### Q23. What are Maven plugins?

**Answer:** Maven plugins provide the implementation of many build operations. Plugins contain goals that perform tasks such as compiling code, running tests, packaging artifacts, generating reports, and deploying artifacts.

| Plugin | Typical purpose |
|---|---|
| **Maven Compiler Plugin** | Compile source code |
| **Maven Surefire Plugin** | Run unit tests |
| **Maven Failsafe Plugin** | Run integration tests |
| **Maven JAR Plugin** | Build JAR artifacts |
| **Maven WAR Plugin** | Build WAR artifacts |
| **Maven Deploy Plugin** | Deploy artifacts |

---

### Q24. What is a Maven plugin goal?

**Answer:** A plugin goal is a specific task provided by a Maven plugin.

For example:

```text
maven-compiler-plugin:compile
```

Here, `maven-compiler-plugin` is the plugin and `compile` is its goal.

A goal can be invoked directly or bound to a lifecycle phase.

---

### Q25. What is the relationship between a lifecycle phase, plugin, and goal?

**Answer:** A **lifecycle phase** defines when a build activity occurs, a **plugin** provides the functionality, and a **goal** is the specific task performed by that plugin.

```text
Lifecycle Phase
      ↓
Plugin
      ↓
Plugin Goal
      ↓
Actual Build Task
```

For example:

```text
compile phase
      ↓
Maven Compiler Plugin
      ↓
compile goal
      ↓
Java source → .class files
```

---

### Q26. What are Maven dependencies?

**Answer:** Maven dependencies are external libraries or artifacts required by a project. Maven reads dependency declarations from `pom.xml`, resolves their required transitive dependencies, and downloads them from configured repositories when they are not already available locally.

---

### Q27. What is a transitive dependency?

**Answer:** A transitive dependency is a dependency required by another dependency. Maven can automatically resolve these dependencies unless they are excluded or otherwise controlled.

```text
Your Application
      ↓
   Library A
      ↓
   Library B
```

If the application depends on Library A and Library A depends on Library B, Maven can resolve Library B automatically.

---

### Q28. What is the difference between `dependencies` and `dependencyManagement`?

**Answer:** `<dependencies>` declares dependencies that the project uses, while `<dependencyManagement>` centralizes dependency versions and related configuration, especially in multi-module projects.

| Feature | `<dependencies>` | `<dependencyManagement>` |
|---|---|---|
| Declares a project dependency | Yes | No, by itself |
| Adds dependency to project classpath | Yes | No, by itself |
| Main purpose | Declare dependencies | Centralize dependency configuration |
| Common use | Direct project dependencies | Multi-module version management |

---

### Q29. What are Maven dependency scopes?

**Answer:** Dependency scope controls where a dependency is available and how it participates in the project's build and runtime dependency graph.

| Scope | Typical meaning |
|---|---|
| `compile` | Available during compilation, testing, and normal runtime |
| `provided` | Needed to compile/test but expected to be supplied by the runtime environment |
| `runtime` | Not needed for compilation but required at runtime |
| `test` | Available only for test compilation and execution |
| `system` | Uses a dependency at a specified local filesystem path; generally discouraged |
| `import` | Used with `pom` dependencies to import dependency management |

---

### Q30. What is the difference between Maven `install` and `deploy`?

**Answer:** `install` places the artifact in the local Maven repository, while `deploy` publishes the artifact to a configured remote repository.

| Command | Destination | Typical purpose |
|---|---|---|
| `mvn install` | `~/.m2/repository` | Make an artifact available to other local builds |
| `mvn deploy` | Remote repository | Share artifacts with CI/CD and other projects |

---

### Q31. What is Maven Central?

**Answer:** Maven Central is a major public repository containing publicly available Maven artifacts and dependencies. Maven can also use private repositories through repository and mirror configuration.

---

### Q32. What is a Maven repository?

**Answer:** A Maven repository is a location from which Maven retrieves artifacts or to which Maven publishes artifacts.

| Repository type | Purpose | Example |
|---|---|---|
| **Local repository** | Cache and store artifacts locally | `~/.m2/repository` |
| **Remote repository** | Shared artifact storage | Nexus, Artifactory |
| **Public repository** | Publicly available artifacts | Maven Central |

---

### Q33. What are Maven profiles?

**Answer:** Maven profiles provide conditional build configuration that can be activated under specific conditions. They are commonly used to vary properties, dependencies, plugins, or repository configuration for environments such as development, testing, or production.

Profiles should be used carefully; sensitive credentials and secrets should not be stored directly in `pom.xml`.

---

### Q34. What is Maven offline mode?

**Answer:** Maven offline mode prevents Maven from accessing remote repositories and makes it use artifacts already available in the local repository.

```bash
mvn -o package
```

Offline mode works only when all required dependencies and plugins are already available locally.

---

### Q35. How would you troubleshoot a Maven dependency resolution failure?

**Answer:** First determine whether the dependency is missing, incorrectly declared, unavailable in the configured repository, blocked by a proxy or mirror, or affected by a corrupted local cache.

Useful commands include:

```bash
mvn dependency:tree
mvn help:effective-pom
mvn -U clean package
```

If a specific artifact in `~/.m2/repository` is corrupted, removing that artifact's local cache and rebuilding can force Maven to download it again.

---

### Q36. What is a SNAPSHOT version in Maven?

**Answer:** A `SNAPSHOT` version represents a development version that can change over time before a final release.

```xml
<version>1.2.0-SNAPSHOT</version>
```

A released version such as `1.2.0` represents a finalized release.

---

### Q37. What is the difference between a SNAPSHOT and a release version?

**Answer:** A SNAPSHOT represents an evolving development version, while a release version represents a finalized version that should remain stable.

| Feature | SNAPSHOT | Release |
|---|---|---|
| Example | `1.2.0-SNAPSHOT` | `1.2.0` |
| Can change over time | Yes | Should not |
| Typical use | Development/integration | Production/release |
| Artifact identity | Ongoing development | Specific release |

---

### Q38. What is the Maven effective POM?

**Answer:** The effective POM is the final Maven configuration after Maven combines the project's `pom.xml` with inherited configuration, parent POMs, active profiles, and other applicable configuration.

It can be inspected with:

```bash
mvn help:effective-pom
```

This is useful for troubleshooting unexpected dependency, plugin, property, and inheritance behavior.

---

### Q39. What is a Maven parent POM?

**Answer:** A parent POM allows common Maven configuration to be inherited by child projects. It can centralize properties, dependency management, plugin management, and other build configuration.

A common use case is a multi-module project:

```text
Parent POM
   |
   ├── service-a
   ├── service-b
   └── service-c
```

---

### Q40. What is the difference between `pluginManagement` and `plugins`?

**Answer:** `<pluginManagement>` defines default plugin configuration and versions for plugins that child projects can use, but it does not by itself execute or activate the plugin. `<plugins>` declares plugins that are part of the project's build.

| Feature | `<pluginManagement>` | `<plugins>` |
|---|---|---|
| Defines plugin version/configuration | Yes | Yes |
| Automatically activates plugin | No | Yes, subject to lifecycle bindings/configuration |
| Common use | Centralize plugin configuration | Use/activate plugins in a project |
| Multi-module benefit | Strong | Project-specific or inherited use |

---

### Q41. How do you run Maven in a CI/CD pipeline?

**Answer:** A typical Maven CI pipeline checks out the source, runs tests and build verification, creates an artifact, performs quality/security checks, and publishes the artifact to a repository.

```text
Checkout
   ↓
mvn clean
   ↓
mvn test
   ↓
mvn package
   ↓
Quality/Security Checks
   ↓
mvn verify
   ↓
Artifact Repository
   ↓
Deployment
```

The CI system can also cache `~/.m2/repository` to reduce repeated dependency downloads.
