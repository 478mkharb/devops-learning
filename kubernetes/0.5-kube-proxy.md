# kube-proxy in Kubernetes

## What is kube-proxy?

**kube-proxy is a node-level Kubernetes networking component that makes Kubernetes Services work.**

The easiest way to remember it:

> **Service gives you a stable address. kube-proxy creates the node networking rules that send traffic from that address to the correct Pod.**

kube-proxy normally runs on **every node**, typically as a DaemonSet.

---

# 1. First Understand the Problem

Pods have their own IP addresses.

For example:

```text
backend-pod-1 → 10.244.1.10
backend-pod-2 → 10.244.2.20
backend-pod-3 → 10.244.3.30
```

But Pod IPs are **not permanent**.

If `backend-pod-2` dies, Kubernetes may create another Pod with a different IP:

```text
Old:
backend-pod-2 → 10.244.2.20

New:
backend-pod-2 → 10.244.4.50
```

Therefore, an application should not depend directly on a Pod IP.

---

# 2. Kubernetes Service Solves the Stable Address Problem

We create a Service:

```text
backend-service
ClusterIP: 10.96.0.50
Port: 80
```

The Service gives clients a **stable virtual IP**.

Instead of calling:

```text
10.244.1.10
```

the frontend can call:

```text
backend-service
```

DNS resolves the Service name to:

```text
10.96.0.50
```

So now we have:

```text
Frontend Pod
     |
     | request to backend-service
     ↓
10.96.0.50  ← Service ClusterIP
```

But there is a problem:

> **10.96.0.50 is not the IP address of a backend Pod.**

So who makes:

```text
10.96.0.50
       ↓
10.244.1.10 / 10.244.2.20 / 10.244.3.30
```

actually happen?

## kube-proxy

---

# 3. What Does kube-proxy Do?

kube-proxy watches Kubernetes networking information such as:

- Services
- EndpointSlices

It learns:

```text
Service:
backend-service
ClusterIP: 10.96.0.50
Port: 80

Endpoints:
10.244.1.10:80
10.244.2.20:80
10.244.3.30:80
```

Then kube-proxy programs the **node's networking rules**.

Conceptually:

```text
Traffic destined for:

10.96.0.50:80

should be sent to one of:

10.244.1.10:80
10.244.2.20:80
10.244.3.30:80
```

---

# 4. Very Important: kube-proxy Does NOT Normally Forward Every Packet

This is the most important concept.

Do **not** imagine the flow as:

```text
Frontend
   ↓
kube-proxy
   ↓
Backend
```

Instead, think:

```text
Frontend
   ↓
Service ClusterIP
   ↓
Linux kernel networking rules
   ↓
Backend Pod
```

kube-proxy's job is mainly to **program/update those rules**.

The Linux kernel handles the actual packet processing.

---

# 5. Simple Analogy

Think of kube-proxy as a person configuring a road junction.

```text
kube-proxy
     |
     | creates/updates routing rules
     ↓
Linux networking subsystem
     |
     | handles actual traffic
     ↓
Backend Pods
```

kube-proxy does not need to stand in the road and personally carry every packet.

It tells the networking subsystem:

> "Traffic coming to this Service should be sent to these backend endpoints."

---

# 6. What Happens When We Create a Service?

Suppose we run:

```bash
kubectl expose deployment backend --port=80
```

## Step 1 — kubectl talks to the API Server

```text
kubectl
   ↓
API Server
```

`kubectl` does not directly configure kube-proxy.

---

## Step 2 — Kubernetes creates the Service

The Service becomes part of Kubernetes cluster state.

For example:

```text
Service:
backend

ClusterIP:
10.96.0.50

Port:
80
```

---

## Step 3 — EndpointSlice identifies the backend Pods

Suppose the Service selector matches three Pods:

```text
10.244.1.10:80
10.244.2.20:80
10.244.3.30:80
```

Kubernetes maintains EndpointSlices containing these endpoints.

Conceptually:

```text
Service
   |
   ↓
EndpointSlice
   |
   +── 10.244.1.10:80
   +── 10.244.2.20:80
   +── 10.244.3.30:80
```

---

## Step 4 — kube-proxy learns about the change

kube-proxy watches the Kubernetes API.

It sees:

```text
Service = 10.96.0.50:80

Endpoints =
10.244.1.10:80
10.244.2.20:80
10.244.3.30:80
```

---

## Step 5 — kube-proxy programs the node

Depending on the configured kube-proxy mode, it programs mechanisms such as:

```text
iptables
IPVS
```

These rules are used by the Linux networking stack.

---

# 7. Actual Traffic Flow

Now the frontend executes:

```bash
curl http://backend-service
```

### First: DNS resolution

The Pod asks CoreDNS:

```text
backend-service
       ↓
10.96.0.50
```

### Then: actual network request

```text
Frontend Pod
      |
      | TCP → 10.96.0.50:80
      ↓
Service ClusterIP
      |
      ↓
Linux kernel networking
      |
      | Service rules
      ↓
One backend endpoint
      |
      ↓
Backend Pod
10.244.2.20:80
```

The selected Pod could be another endpoint on the next request.

---

# 8. What Happens When a Pod Dies?

Initially:

```text
Service
10.96.0.50
    |
    +── Pod A → 10.244.1.10
    +── Pod B → 10.244.2.20
    +── Pod C → 10.244.3.30
```

Suppose Pod B dies.

Kubernetes updates the EndpointSlice:

```text
Service
10.96.0.50
    |
    +── Pod A → 10.244.1.10
    +── Pod C → 10.244.3.30
```

kube-proxy detects the change and updates the node's networking rules.

Now traffic is directed only toward the current endpoints.

```text
Client
  ↓
Service
  ↓
Linux kernel rules
  ↓
Pod A / Pod C
```

This is why applications can continue using the same Service even though backend Pod IPs change.

---

# 9. Why Does kube-proxy Run on Every Node?

kube-proxy normally runs on every node:

```text
Node 1
 └── kube-proxy

Node 2
 └── kube-proxy

Node 3
 └── kube-proxy
```

Each node needs the appropriate Service networking rules because Pods on that node may send traffic to Services.

For example:

```text
Node 1
 ├── frontend Pod
 └── kube-proxy

Node 2
 ├── backend Pod
 └── kube-proxy
```

The frontend Pod on Node 1 can send traffic to a Service whose backend Pod is on Node 2.

The networking rules on the nodes make this possible.

---

# 10. kube-proxy and CoreDNS Are Different

This distinction is important.

## CoreDNS

CoreDNS answers:

> **"What IP address belongs to this Service name?"**

Example:

```text
backend-service
      ↓
10.96.0.50
```

## kube-proxy

kube-proxy helps implement:

> **"Where should traffic sent to 10.96.0.50 actually go?"**

Example:

```text
10.96.0.50
      ↓
10.244.1.10
```

So:

```text
CoreDNS
   ↓
Name → Service IP

kube-proxy
   ↓
Service IP → Backend endpoint
```

---

# 11. kube-proxy and EndpointSlice

Do not confuse these two.

### EndpointSlice

Contains information about **which Pods/endpoints currently back a Service**.

Example:

```text
EndpointSlice
 ├── 10.244.1.10:80
 ├── 10.244.2.20:80
 └── 10.244.3.30:80
```

### kube-proxy

Uses Service and endpoint information to configure networking rules on the node.

```text
Service + EndpointSlice
          ↓
      kube-proxy
          ↓
   Node networking rules
```

---

# 12. What If kube-proxy Stops Running?

This depends on the networking implementation and what rules were already programmed.

The important interview point is:

> **Existing kernel rules may continue to handle traffic for some time, but kube-proxy is no longer able to keep those rules synchronized with changing Services and endpoints.**

For example, if a Pod dies while kube-proxy is unavailable, the node may not immediately receive the corresponding rule update.

Therefore:

```text
kube-proxy healthy
       ↓
rules stay synchronized
       ↓
Service traffic follows current endpoints
```

Whereas:

```text
kube-proxy unavailable
       ↓
rules stop being reconciled
       ↓
Service behavior can become stale/broken
```

---

# 13. iptables and IPVS

Historically, kube-proxy has used different mechanisms to implement Service networking.

Common concepts you may encounter are:

```text
iptables mode
IPVS mode
```

The important idea for now is:

```text
kube-proxy
     ↓
programs node networking rules
     ↓
Linux kernel
     ↓
Service traffic reaches endpoints
```

You do not need to memorize the detailed rule chains until the basic flow is clear.

# Quick Interview Questions

### Q1. Is kube-proxy a normal network proxy that receives every packet?

**No.** In the common model, kube-proxy programs node networking rules; the Linux kernel handles the packet processing.

### Q2. Who resolves `backend-service` to its ClusterIP?

**CoreDNS.**

### Q3. Who knows which Pods currently back the Service?

**EndpointSlices contain the endpoint information.**

### Q4. Who programs the node's Service networking rules?

**kube-proxy.**

### Q5. Who actually processes/forwards the packets after the rules are installed?

**The Linux kernel/networking subsystem.**

### Q6. Why can the Service IP remain stable when Pod IPs change?

Because the Service provides the stable virtual IP, while the endpoint information and node networking rules are updated as Pods change.

> **Remember: CoreDNS answers "WHAT IP?" — kube-proxy helps answer "WHERE DOES THAT SERVICE TRAFFIC GO?"**## Why is kube-proxy Required in a Kubernetes Cluster?

kube-proxy is a **node-level networking component** that makes Kubernetes **Services actually work**. A Service by itself is only a logical object stored in the cluster; kube-proxy turns it into real network traffic routing.

---

## Why kube-proxy Is Required

Pods in Kubernetes:

* Have **dynamic IP addresses**
* Can be **restarted or rescheduled** at any time
* Can run on **any node**

Applications, however, need:

* A **stable IP or DNS name**
* **Load balancing** across multiple Pods
* Seamless traffic routing even when Pods change

👉 Kubernetes Services provide a stable abstraction.
👉 **kube-proxy is required to implement that abstraction at the network level.**

Without kube-proxy, Services would exist only as API objects and would not forward traffic.

---

## What kube-proxy Does (Conceptually)

kube-proxy:

* Runs on **every node** as a DaemonSet
* Watches the **API Server** for:

  * Services
  * Endpoints / EndpointSlices
* Creates and updates **network rules on the node** so Service traffic reaches Pods

kube-proxy does **not** forward packets itself. The Linux kernel does that.

---

## What Happens When You Create a Service via kubectl

### Step 1: You Apply a Service

```bash
kubectl apply -f service.yaml
```

or

```bash
kubectl expose deployment web --port=80
```

`kubectl`:

* Sends a REST request to the **API Server**
* Does not configure networking

---

### Step 2: Service Is Stored in the Cluster

The API Server:

* Validates the Service
* Stores it in **etcd**

Example:

```text
Service: web-service
ClusterIP: 10.96.0.50
Port: 80
```

At this point:

* Service exists only as **cluster state**
* No iptables or IPVS rules exist yet

---

### Step 3: Endpoints Are Created

The EndpointSlice controller:

* Finds Pods matching the Service selector
* Creates EndpointSlices

Example:

```text
Endpoints for web-service:
- 10.244.1.10:80
- 10.244.2.15:80
```

Now the API Server knows:

* Which Pods back the Service

---

## How kube-proxy Handles the Service

### Step 4: kube-proxy Detects the Change

On every node, kube-proxy:

* Watches the API Server
* Sees the new Service and its Endpoints

This is where **kube-proxy comes into the picture**.

---

### Step 5: kube-proxy Programs Network Rules

kube-proxy:

* Reads Service IP + Endpoint IPs
* Calculates required forwarding rules
* Writes rules into the **node’s Linux kernel**

Depending on mode:

* **iptables mode** → NAT rules
* **IPVS mode** → Kernel load balancer entries

📌 The rules live in the kernel, not in kube-proxy.

---

## Where the Service Rules Exist

### iptables mode (default)

Rules exist in:

* Linux kernel netfilter (iptables)
* Chains such as:

  * `KUBE-SERVICES`
  * `KUBE-SVC-*`
  * `KUBE-SEP-*`

### IPVS mode

Rules exist in:

* Linux kernel IPVS tables

---

## Traffic Flow After Rules Are Created

```text
Client Pod
   |
   v
Service IP (ClusterIP)
   |
Linux kernel (iptables / IPVS rules)
   |
Selected Pod IP
```

kube-proxy is **not in the data path**. It only updates rules.

---

## What Happens When Pods Change

If a Pod:

* Dies
* Is added
* Changes IP

Then:

1. EndpointSlice is updated
2. kube-proxy detects the update
3. kube-proxy updates kernel rules
4. Traffic automatically flows to healthy Pods

---

## What Breaks If kube-proxy Is Not Running

* ClusterIP Services stop routing
* NodePort Services stop routing
* LoadBalancer backends fail

Pods can still communicate via direct IPs, but **Services stop working**.

---

## End-to-End Summary

```text
kubectl
  ↓
API Server
  ↓
etcd (Service + Endpoints)
  ↓
kube-proxy (watching API Server)
  ↓
iptables / IPVS rules in kernel
  ↓
Linux kernel forwards traffic to Pods
```

---

## One-Line Interview Answer

> kube-proxy is required because it converts Kubernetes Services from logical API objects into real network routing by programming iptables or IPVS rules on every node based on Service and Endpoint changes.
