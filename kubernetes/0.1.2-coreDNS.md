# DNS in Kubernetes

This document explains **how DNS works inside a Kubernetes cluster**, **what CoreDNS does**, **what `/etc/resolv.conf` does**, and **how normal and Headless Services differ**.

The goal is to keep the flow simple and interview-friendly.

---

## Why DNS Is Needed in Kubernetes

Pods get **dynamic IP addresses**.

For example:

```text
backend Pod
IP = 10.244.1.15
```

If the Pod is deleted and recreated:

```text
backend Pod
IP = 10.244.2.20
```

The application should not depend directly on the Pod IP.

Kubernetes therefore provides **Services and DNS** so applications can communicate using stable names.

Instead of:

```bash
curl http://10.244.1.15:8080
```

the application can use:

```bash
curl http://backend:8080
```

---

# What Is CoreDNS?

**CoreDNS is the DNS server used by Kubernetes for cluster DNS and service discovery.**

It normally runs as Pods in:

```text
kube-system
```

and is accessed through a Kubernetes Service commonly named:

```text
kube-dns
```

Important distinction:

```text
kube-dns = Kubernetes Service name
CoreDNS  = DNS server running behind that Service
```

You normally do not create CoreDNS Pods manually.

---

# What Is `/etc/resolv.conf`?

Every normal Kubernetes Pod has:

```text
/etc/resolv.conf
```

This file contains the **DNS resolver configuration for that Pod**.

Check it with:

```bash
kubectl exec -it <pod-name> -- cat /etc/resolv.conf
```

A typical example is:

```text
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

## `nameserver`

For example:

```text
nameserver 10.96.0.10
```

This tells the Pod's DNS resolver:

> Send DNS queries to this DNS server.

In a typical Kubernetes cluster, `10.96.0.10` would be the ClusterIP of the `kube-dns` Service.

The important point is:

```text
/etc/resolv.conf
        |
        | tells the Pod WHERE to ask DNS
        v
kube-dns Service
        |
        v
CoreDNS
```

## `search`

For example:

```text
search default.svc.cluster.local svc.cluster.local cluster.local
```

This allows an application to use a short name:

```bash
curl http://backend
```

instead of always specifying:

```text
backend.default.svc.cluster.local
```

## Important Interview Point

`/etc/resolv.conf` **does not contain all Kubernetes Service IPs or Pod IPs**.

It mainly tells the Pod's resolver:

```text
WHERE should I send my DNS query?
```

| Component | Value |
|---|---|
| Source Pod | `frontend` |
| Target Service | `backend` |

| Backend Pod-1 IP | `10.244.1.15` |
| Backend Pod-2 IP | `10.244.2.20` |

# Simple DNS Resolution Flow

Suppose the frontend Pod runs:

```bash
curl http://backend
```

## Step 1: Application Makes a Request

The application wants to communicate with:

```text
backend
```

It does not know the Service IP.

It asks the operating system's DNS resolver:

> "What IP address does `backend` mean?"

---

## Step 2: Pod Uses `/etc/resolv.conf`

The Pod's resolver reads:

```text
nameserver 10.96.0.10
```

Therefore the DNS query is sent to:

```text
10.96.0.10
```

which is the `kube-dns` Service IP in this example.

---

## Step 3: kube-dns Service Sends the Query to CoreDNS

The flow is:

```text
frontend Pod
     |
     | DNS query
     v
kube-dns Service
10.96.0.10
     |
     v
CoreDNS
```

The `kube-dns` Service provides a stable endpoint for the DNS server Pods.

---

## Step 4: CoreDNS Resolves the Service Name

CoreDNS watches Kubernetes information through the Kubernetes API.

For Service discovery, the important resources include:

```text
Services
EndpointSlices
```

For our example, CoreDNS can resolve:

```text
backend.default.svc.cluster.local
                |
                v
          10.96.120.45
```

---

## Step 5: DNS Response Is Returned

CoreDNS returns:

```text
10.96.120.45
```

to the frontend Pod.

Now the application knows the IP of the **backend Service**.

---

## Step 6: Actual Application Traffic Starts

The frontend now sends the HTTP request to:

```text
10.96.120.45
```

This is the **Service ClusterIP**.

The flow is now:

```text
frontend Pod
     |
     | HTTP request
     v
backend Service
10.96.120.45
```

---

## Step 7: Service Routes Traffic to a Backend Pod

Suppose the backend Pods are:

```text
backend-1 → 10.244.1.15
backend-2 → 10.244.2.20
```

The Service has these Pods as endpoints.

Kubernetes Service networking sends the request to one of the available endpoints.

Conceptually:

```text
10.96.120.45
(Service ClusterIP)
       |
       +------> 10.244.1.15
       |
       +------> 10.244.2.20
```

---

# Important: Service IP vs Pod IP

This is a very common interview question.

## Does every Pod behind a Service have the same IP?

**No.**

Every Pod has its **own Pod IP**.

Example:

```text
backend Service
ClusterIP = 10.96.120.45

       |
       +---- backend-1 → 10.244.1.15
       |
       +---- backend-2 → 10.244.2.20
       |
       +---- backend-3 → 10.244.3.25
```

Therefore:

```text
ONE Service
ONE ClusterIP

MANY Pods
MANY Pod IPs
```

The Service ClusterIP is a **stable virtual IP**.

The Pod IPs are **individual and can change**.

# Where Does CoreDNS Get Service and Endpoint Information?

CoreDNS does not normally maintain a simple text file containing all Pod IPs.

The high-level flow is:

```text
                 kube-apiserver
                      |
          +-----------+-----------+
          |                       |
       Services              EndpointSlices
          |                       |
          +-----------+-----------+
                      |
                      v
                   CoreDNS
```

Kubernetes cluster state is persisted through the API server in **etcd**.

A Pod object can contain its IP:

```yaml
status:
  podIP: 10.244.1.15
```

For Service-to-Pod endpoint discovery, **EndpointSlices** are especially important.

Check them with:

```bash
kubectl get endpointslices
```

or:

```bash
kubectl get endpointslice -o yaml
```

Think of it as:

```text
Pod IP information
       |
       v
Kubernetes API / EndpointSlice
       |
       v
CoreDNS
       |
       v
DNS answer
```

CoreDNS watches Kubernetes resources and maintains the DNS information it needs.

# Normal Service

A normal Service has a ClusterIP.

Example:

```text
backend Service
ClusterIP = 10.96.120.45
```

The DNS flow is:

```text
frontend
   |
   | DNS query: backend
   v
CoreDNS
   |
   | returns 10.96.120.45
   v
backend Service
   |
   | Service networking
   v
backend Pod
```

In short:

```text
DNS → ClusterIP → Pod
```

---

# Headless Service

A Headless Service is a Service configured with:

```yaml
clusterIP: None
```

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  clusterIP: None
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8080
```

A Headless Service does **not** have a virtual ClusterIP.

Instead, DNS can return the IP addresses of the Service's endpoints.

Suppose:

```text
backend-1 → 10.244.1.15
backend-2 → 10.244.2.20
backend-3 → 10.244.3.25
```

Then the Service DNS name can resolve to endpoint IPs:

```text
backend.default.svc.cluster.local
              |
       +------+------+------+
       |             |      |
       v             v      v
  10.244.1.15   10.244.2.20 10.244.3.25
```

In short:

```text
DNS → Endpoint Pod IP(s)
```

There is **no ClusterIP in the middle**.

---

# Why Use a Headless Service?

A Headless Service is useful when an application needs to discover **individual endpoints**, rather than only accessing a single virtual Service IP.

It is commonly used with:

```text
StatefulSets
Distributed databases
Distributed systems
```

Examples include:

```text
ScyllaDB
Cassandra
Kafka
```

The exact DNS records depend on the workload and Service configuration.

---

# StatefulSet + Headless Service

StatefulSets provide stable Pod identities:

```text
scylla-0
scylla-1
scylla-2
```

With a Headless Service, Kubernetes DNS can provide stable DNS identities for individual StatefulSet Pods.

Conceptually:

```text
scylla-0.scylla.default.svc.cluster.local
scylla-1.scylla.default.svc.cluster.local
scylla-2.scylla.default.svc.cluster.local
```

The important relationship is:

```text
StatefulSet
     +
Headless Service
     |
     v
Stable Pod identity + DNS discovery
```

# Normal Service vs Headless Service

| Feature | Normal Service | Headless Service |
|---|---|---|
| `clusterIP` | Allocated | `None` |
| Virtual ClusterIP | Yes | No |
| DNS commonly returns | ClusterIP | Endpoint Pod IPs |
| Service networking via virtual IP | Yes | No virtual ClusterIP |
| Common use | Normal application communication | Endpoint discovery |
| Common with StatefulSet | Possible | Very common |

### Normal Service

```text
DNS
 |
 v
ClusterIP
 |
 v
Pod
```

### Headless Service

```text
DNS
 |
 v
Endpoint Pod IP(s)
```

# How to Troubleshoot Kubernetes DNS

## 1. Check `/etc/resolv.conf`

```bash
kubectl exec -it <pod-name> -- cat /etc/resolv.conf
```

Check:

```text
nameserver
search
options
```

---

## 2. Check kube-dns Service

```bash
kubectl get svc -n kube-system
```

Look for:

```text
kube-dns
```

---

## 3. Check CoreDNS Pods

```bash
kubectl get pods -n kube-system -l k8s-app=kube-dns
```

---

## 4. Check CoreDNS Logs

```bash
kubectl logs -n kube-system -l k8s-app=kube-dns
```

---

## 5. Test DNS From a Pod

```bash
kubectl exec -it <pod-name> -- nslookup backend
```

If `nslookup` is unavailable, use:

```bash
kubectl exec -it <pod-name> -- getent hosts backend
```

---

## 6. Check the Service

```bash
kubectl get svc backend
kubectl describe svc backend
```

---

## 7. Check EndpointSlices

```bash
kubectl get endpointslices
```

For a specific Service:

```bash
kubectl get endpointslices -l kubernetes.io/service-name=backend
```

# Three IPs You Must Not Confuse

| IP | Belongs to | Purpose |
|---|---|---|
| `10.96.0.10` | `kube-dns` Service | Entry point for DNS queries |
| `10.96.120.45` | `backend` Service | Stable virtual ClusterIP |
| `10.244.1.15` | `backend` Pod | IP of one specific Pod |

Remember:

```text
10.96.0.10
     ↓
kube-dns Service
     ↓
CoreDNS
```

```text
10.96.120.45
     ↓
backend Service
     ↓
backend Pods
```

```text
10.244.1.15
     ↓
one specific backend Pod
```

# Key Points to Remember

1. **Pod IPs are dynamic.**
2. **Services provide stable application endpoints.**
3. **CoreDNS provides Kubernetes DNS/service discovery.**
4. **`/etc/resolv.conf` tells a Pod where to send DNS queries.**
5. **`/etc/resolv.conf` does not contain all Service or Pod IP mappings.**
6. **`kube-dns` is the Service name; CoreDNS is the DNS server.**
7. **A normal Service has a ClusterIP.**
8. **Pods behind the same Service do NOT have the same IP.**
9. **Each Pod has its own Pod IP.**
10. **A Headless Service uses `clusterIP: None`.**
11. **A Headless Service has no virtual ClusterIP.**
12. **DNS can return endpoint Pod IPs for a Headless Service.**
13. **Headless Services are commonly used with StatefulSets.**
14. **EndpointSlices are important for Service endpoint discovery.**

# Interview Questions

## Q1. What is `/etc/resolv.conf`?

> It contains DNS resolver configuration for the Pod, including the DNS server address, search domains, and resolver options.

## Q2. What is the use of `nameserver` in `/etc/resolv.conf`?

> It tells the Pod's DNS resolver which DNS server should receive DNS queries.

## Q3. Does `/etc/resolv.conf` contain Service IPs?

> No. It contains resolver configuration, not the complete list of Kubernetes DNS records.

## Q4. What is CoreDNS?

> CoreDNS is the DNS server used by Kubernetes for cluster DNS and service discovery.

## Q5. What is `kube-dns`?

> `kube-dns` is the Kubernetes DNS Service that provides a stable Service endpoint for the cluster DNS implementation, commonly CoreDNS.

## Q6. Do all Pods behind a Service have the same IP?

> No. Each Pod has its own Pod IP. The Service has one stable ClusterIP that represents the Service.

## Q7. What is a Headless Service?

> A Service with `clusterIP: None`. It has no virtual ClusterIP, and DNS can return the IP addresses of its endpoints.

## Q8. Why do we use a Headless Service?

> It is commonly used for endpoint discovery and stable Pod identities, especially with StatefulSets and distributed stateful applications.

## Q9. What is an EndpointSlice?

> EndpointSlice is the scalable Kubernetes API representation of the network endpoints associated with a Service.

## Q10. What is the normal Service DNS flow?

> Pod → `/etc/resolv.conf` → `kube-dns` Service → CoreDNS → Service ClusterIP → Service networking → backend Pod.

## Q11. What is the Headless Service DNS flow?

> Pod → `/etc/resolv.conf` → `kube-dns` Service → CoreDNS → endpoint Pod IP(s).

# One-Line Summary

> **Pod → `/etc/resolv.conf` → kube-dns Service → CoreDNS → DNS answer → Service/Endpoint**

For a **normal Service**:

```text
DNS → ClusterIP → Pod
```

For a **Headless Service**:

```text
DNS → Endpoint Pod IP(s)
```
