# Kubernetes Networking From Scratch (Step 1 → Step 16)

This document explains **Kubernetes networking from absolute basics to cross‑node Pod communication**. The diagrams are written as **clear architecture flows** so you can visualize what happens inside a Kubernetes node and cluster.

---

# Step 1 — Fundamental Rule: Every Pod Gets Its Own IP

Traditional server model:

```
Server (10.0.0.5)
 ├─ App1 → 10.0.0.5:8080
 ├─ App2 → 10.0.0.5:9090
 └─ App3 → 10.0.0.5:7070
```

Applications share the **same machine IP**, therefore **ports distinguish services**.

Kubernetes networking model:

```
Node
 ├─ PodA → 10.244.1.2
 ├─ PodB → 10.244.1.3
 └─ PodC → 10.244.1.4
```

Communication becomes:

```
PodA → PodB
10.244.1.2 → 10.244.1.3
```

No port translation required.

Kubernetes networking rules:

1. Every Pod has its own IP
2. Pods communicate without NAT
3. Containers inside a Pod share networking

---

# Step 2 — Containers Inside a Pod Share Networking

A Pod can contain multiple containers.

Example:

```
Pod (IP = 10.244.1.5)

 ├─ Container A
 └─ Container B
```

Both containers share:

* same IP address
* same network interfaces
* same ports
* same routing table

Example communication:

```
Container A → localhost:8080 → Container B
```

This works because they share the **same network namespace**.

---

# Step 3 — Linux Network Namespace

Kubernetes uses **Linux network namespaces** for isolation.

A namespace provides its own:

* interfaces
* IP addresses
* routing table
* ARP table
* firewall rules

Example:

```
Namespace A
  eth0 → 10.0.0.1

Namespace B
  eth0 → 10.0.0.2
```

Even on the same machine they behave like **separate hosts**.

---

# Step 4 — How the Network Namespace Is Created

Container runtimes create network namespaces using a Linux system call:

```
clone(CLONE_NEWNET)
```

This instructs the kernel to create a **new network stack for the container**.

# Step 5 — Pod Creation Control Flow

When you create a Pod:

```
kubectl apply
      ↓
API Server
      ↓
Scheduler
      ↓
Node selected
      ↓
kubelet
      ↓
container runtime
```

The runtime then creates the **Pod sandbox**.

---

# Step 6 — Pause Container (Pod Sandbox)

Kubernetes creates a **pause container first**.

This container:

* owns the Pod network namespace
* keeps the namespace alive

```
Pod

 ├─ Pause Container
 │     └─ holds network namespace
 │
 ├─ Application Container
 │
 └─ Sidecar Container
```

All containers join the **same namespace**.

Result:

```
Shared Pod IP
Shared interfaces
Shared ports
```

---

# Step 7 — CNI Plugin Configures Networking

After the pause container starts:

```
kubelet
  ↓
CNI plugin
```

The CNI plugin performs:

* network attachment
* veth creation
* IP allocation

Examples of CNI:

* Flannel
* Calico
* Weave

---

# Step 8 — veth Pair Creation

A **veth pair** acts like a virtual ethernet cable.

```
vethA  <================>  vethB
```

Kubernetes setup:

```
Pod Namespace               Host Namespace

eth0   <================>   veth123
```

Inside Pod:

```
eth0
```

On host:

```
veth123
```

---

# Step 9 — Linux Bridge (cni0)

All veth interfaces connect to a Linux bridge called:

```
cni0
```

Architecture inside node:

```
                 Node

            ┌─────────────┐
            │    cni0     │
            │   (bridge)  │
            └─────┬───────┘
                  │
      ┌───────────┼───────────┐
      │           │           │
    vethA       vethB       vethC
      │           │           │
     Pod1        Pod2        Pod3
   10.244.1.2  10.244.1.3  10.244.1.4
```

The bridge behaves like a **virtual Layer‑2 switch**.

# Step 12 — Pod CIDR Allocation

Each node receives a Pod CIDR block.

Example cluster:

```
Node1 → 10.244.1.0/24
Node2 → 10.244.2.0/24
```

Pods on Node1:

```
10.244.1.x
```

Pods on Node2:

```

```

# Step 13 — Cross Node Communication Problem

Example:

```
PodA → 10.244.1.5 (Node1)
PodB → 10.244.2.7 (Node2)
```

Node1 must know how to reach:

```
10.244.2.0/24
```

This is solved by the **CNI networking layer**.

---

# Step 14 — Overlay Networking (Flannel VXLAN)

Overlay networking wraps Pod packets inside node packets.

Original packet:

```
10.244.1.5 → 10.244.2.7
```

Encapsulated packet:

```
192.168.1.10 → 192.168.1.11
```

Meaning:

```
Pod packet travels inside node packet
```

# Step 16 — Routing Model (Calico)

Calico avoids encapsulation and uses routing.

Example route on Node1:

```
10.244.2.0/24 via 192.168.1.11
```

Packet flow:

```
PodA
 │
 ▼
eth0
 │
 ▼
veth
 │
 ▼
cni0
 │
 ▼
Node routing table
 │
 ▼
Node2
 │
 ▼
cni0
 │
 ▼
veth
 │
 ▼
PodB
```

No VXLAN encapsulation is required.

# Step 17 — Kubernetes Service Networking

Pods are **ephemeral**. When a Pod restarts it may receive a **new IP address**. Applications therefore cannot reliably connect directly to Pod IPs.

Kubernetes solves this using a **Service**.

A Service provides:

* a stable virtual IP (ClusterIP)
* load balancing across Pods
* service discovery

Example:

```
Pods

Pod1 → 10.244.1.3
Pod2 → 10.244.2.7
Pod3 → 10.244.3.9
```

Service:

```
payment-service
ClusterIP → 10.96.0.25
```

Applications call:

```
10.96.0.25
```

Kubernetes routes the request to one of the Pods.

---

# Service Architecture

```
Client Pod
    │
    ▼
Service VIP (ClusterIP)
    │
    ▼
kube-proxy
    │
    ▼
iptables rules
    │
    ▼
One of the backend Pods
```

---

# kube-proxy

kube-proxy runs on every node and programs **iptables rules** that implement Service load balancing.

Responsibilities:

* watch Service objects
* watch Endpoint objects
* update iptables rules

# Final Summary

Pod networking in Kubernetes works through several layers:

1. Pod scheduled to node
2. Pause container creates network namespace
3. CNI attaches Pod to network
4. veth pair connects Pod to host
5. Linux bridge connects Pods on same node
6. Pod CIDR provides IP range
7. CNI networking enables cross‑node routing

This creates a **flat Pod network across the entire Kubernetes cluster**.
