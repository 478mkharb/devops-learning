# LangChain Learning Notes - Part 1

> Beginner-friendly notes created while learning LangChain step by step.

| Question | Answer |
|----------|--------|
| What is LangChain? | LangChain is an open-source Python framework used to build applications powered by Large Language Models (LLMs). It provides reusable components like Models, Prompts, Output Parsers, Memory, Tools, Agents, and Chains so developers don't have to write everything from scratch. |
| Is LangChain a Python script? | No. LangChain is **not** a Python script. It is a **Python library/framework** that you install using `pip install langchain`. |
| Is LangChain an LLM? | No. LangChain is **not** an LLM. It simply works with LLMs like GPT, Claude, Gemini, Llama, Mistral, etc. |
| Is LangChain an LLM Model? | No. Models like GPT-4o, Llama 3.2, Claude, Gemini are LLMs. LangChain only provides a common interface to use them. |
| Why do we use LangChain? | Without LangChain, developers would have to manually build prompts, call APIs, parse responses, manage conversation history, execute tools, and build agents. LangChain provides reusable components to simplify these tasks. |
| What are the main components of LangChain? | Prompt Templates, Chat Prompt Templates, Models, Output Parsers, Memory, Chains, Tools, Agents, Document Loaders, Vector Stores, Retrievers and LangChain Runtime. |
| What is a Model in LangChain? | A Model is an object that communicates with an LLM provider. It sends prompts to the LLM and returns the response. |
| Does LangChain contain the model? | No. LangChain does not contain the LLM. It connects to external models like OpenAI GPT, Ollama Llama, Claude or Gemini through their APIs. |
| What is ChatOllama? | ChatOllama is a LangChain integration class that allows LangChain to communicate with an Ollama server running locally. |
| Is ChatOllama an MCP Server? | No. ChatOllama is simply an adapter between LangChain and Ollama. It is not an MCP server. |
| What is Ollama? | Ollama is a local inference server that lets you run open-source LLMs such as Llama 3.2 on your own computer without calling a cloud API. |
| Is Llama 3.2 free? | Yes. Llama 3.2 is an open-weight model that can be downloaded and executed locally using Ollama without paying API charges. |
| What happens when we create a model object? | LangChain creates a Python object that knows how to communicate with a particular LLM provider. No request is sent to the model yet. |
| When does the LLM actually get called? | The LLM is contacted only when methods like `.invoke()` are executed. Creating the model object alone does not contact the model. |
| What is PromptTemplate? | PromptTemplate is a reusable text template that contains placeholders. You replace placeholders with actual values before sending the prompt to the model. |
| Why use PromptTemplate instead of writing strings? | It allows the same prompt to be reused with different values without rewriting the prompt each time. |
| Example of PromptTemplate | `"Explain {topic} in simple words."` where `{topic}` is replaced with values like Kubernetes, Docker or Python. |
| What is ChatPromptTemplate? | ChatPromptTemplate creates chat conversations consisting of multiple roles such as System, Human and AI messages. |
| Difference between PromptTemplate and ChatPromptTemplate? | PromptTemplate generates one text prompt, whereas ChatPromptTemplate generates structured chat messages with different roles. |
| What is a System Message? | A System Message defines the behaviour of the AI. Example: "You are a helpful DevOps tutor." |
| What is a Human Message? | It represents the user's input or question. |
| What is an AI Message? | It represents the model's response. In LangChain it is stored as an `AIMessage` object. |
| What is AIMessage? | AIMessage is a Python object returned by LangChain after an LLM call. It contains the generated response and additional metadata. |
| What is `response.content`? | `content` is an attribute (field) inside the AIMessage object that stores the actual text generated by the LLM. |
| Why do we use `response.content`? | Because the model returns an AIMessage object, not a plain string. The actual answer is stored inside its `content` field. |
| What is an Output Parser? | An Output Parser converts the raw model response into the format required by your application. |
| Why use StrOutputParser? | The model returns an AIMessage object. `StrOutputParser()` extracts only the text so you don't need to write `response.content` manually every time. |
| What is LCEL? | LCEL (LangChain Expression Language) is a pipeline syntax that connects multiple LangChain components using the `|` operator. |
| Example of LCEL | `prompt \| model \| StrOutputParser()` |
| Why is LCEL useful? | It lets developers connect prompts, models, parsers and other components into readable pipelines with very little code. |
| What is a Chain? | A Chain is a sequence of components where the output of one component becomes the input of the next component. |
| How does a Chain work? | Prompt → Model → Output Parser → Final Answer. Each component passes its output to the next one automatically. |
| What is Memory in LangChain? | Memory stores previous conversation messages so they can be sent back to the LLM during future requests. |
| Does the LLM remember previous conversations? | No. LLMs are stateless. They forget everything after each API call. |
| Then how does conversation memory work? | LangChain stores previous messages and sends them again with every new request so the LLM appears to remember the conversation. |
| What is `InMemoryChatMessageHistory`? | It is a simple memory implementation that stores chat messages in RAM during program execution. |
| What happens if the program stops? | InMemoryChatMessageHistory is cleared because it only exists in memory. Persistent memory requires databases or other storage. |
| What is the placeholder `history` in ChatPromptTemplate? | It is the location where LangChain inserts previous conversation messages before sending the request to the model. |
| What is the learning sequence followed? | **Model → Prompt → PromptTemplate → ChatPromptTemplate → Output Parser → LCEL → Memory → Chains → Agents** |
| What important concept should I remember? | LangChain itself does not generate answers. The LLM generates answers. LangChain only organizes prompts, models, memory, tools, chains and agents into reusable building blocks. |
| What is the biggest takeaway from Part 1? | LangChain is a framework that provides reusable components for working with LLMs. Before learning Agents, understand Models, Prompts, Output Parsers, Memory and Chains because Agents are built using all of these components. |

---

## Key Revision Notes

- LangChain is a **Python Framework**, not an LLM.
- LLMs perform the reasoning.
- LangChain organizes the workflow.
- PromptTemplate creates reusable prompts.
- ChatPromptTemplate creates chat conversations.
- AIMessage stores the model response.
- `response.content` contains the generated text.
- StrOutputParser extracts plain text.
- LCEL connects components using the `|` operator.
- Chains connect multiple LangChain components together.
- Memory stores previous messages because LLMs are stateless.
- Understanding these concepts is essential before learning Agents.

# LangChain Learning Notes - Part 2

> **Topic:** AI Agents, Tools, LangChain Runtime, ReAct Loop

| Question | Answer |
|----------|--------|
| What is an AI Agent? | An AI Agent is an application that uses an LLM to reason, decide which tools to use, execute those tools, observe the results, and continue until it reaches the goal. |
| How is an AI Agent different from a normal LLM call? | A normal LLM call generates only one response. An AI Agent can reason, call tools, use previous results, and perform multiple steps before giving the final answer. |
| What is the difference between a Basic LLM Call and an Agent? | Basic LLM: **Input → Model → Output**. Agent: **Reason → Act → Observe → Repeat** until the task is complete. |
| What is the ReAct pattern? | ReAct stands for **Reason → Act → Observe**. The LLM first reasons about the problem, decides an action, executes a tool through LangChain, observes the result, and repeats if necessary. |
| Can an LLM execute Python code directly? | No. An LLM cannot execute Python code. It can only decide which tool should be executed and request that action. |
| Who executes the Python function? | The **LangChain Runtime** executes the Python function after receiving the tool call from the LLM. |
| What is a Tool? | A Tool is simply a Python function that an AI Agent is allowed to execute. It extends the capabilities of the LLM beyond text generation. |
| Why do we need Tools? | LLMs cannot interact with databases, APIs, files, Kubernetes, or cloud resources by themselves. Tools allow them to perform real-world actions. |
| What kind of operations can Tools perform? | Query databases, call REST APIs, restart Kubernetes pods, provision cloud resources, read/write files, send emails, execute shell commands, and much more. |
| What is the `@tool` decorator? | `@tool` tells LangChain to register a Python function as an Agent Tool and automatically generate a schema that the LLM can understand. |
| Why is a docstring important in a Tool? | The docstring describes what the tool does. The LLM reads this description to decide whether the tool should be used. |
| Why are type hints important in Tools? | Type hints allow LangChain to generate the input schema (JSON Schema) so the LLM knows what arguments are expected. |
| Example of a Tool | ```python\n@tool\ndef restart_pod(namespace: str, pod_name: str):\n    ...\n``` |
| Can a Tool be any Python function? | Yes. As long as it is decorated with `@tool`, LangChain can expose it to the LLM. |
| What happens if a function is not decorated with `@tool`? | It remains a normal Python function and will not be visible to the Agent. |
| What is `create_agent()`? | `create_agent()` creates an AI Agent by combining an LLM with one or more Tools. |
| Does `create_agent()` call the LLM? | No. It only creates the Agent object. The LLM is contacted later when `agent.invoke()` is executed. |
| What is stored inside the Agent? | The selected model, the list of registered tools, internal configuration, and the execution workflow. |
| What is `agent.invoke()`? | It starts the Agent execution. This is where the LangChain Runtime begins reasoning, calling the model, executing tools, and producing the final answer. |
| Does `agent.invoke()` directly execute Python functions? | No. It first sends the user's request to the LLM. Only if the LLM requests a tool does LangChain execute the corresponding Python function. |
| What happens when `agent.invoke()` is called? | LangChain prepares the prompt, sends it to the LLM, receives tool requests (if any), executes Python functions, sends results back to the LLM, and repeats until the LLM returns the final answer. |
| What is LangChain Runtime? | LangChain Runtime is the execution engine inside the LangChain framework. It manages prompt creation, API calls, tool execution, conversation flow, retries, and assembling the final response. |
| Is LangChain Runtime a separate package? | No. It is an internal execution engine that is part of the LangChain framework. |
| Difference between LangChain and LangChain Runtime? | **LangChain** is the framework. **LangChain Runtime** is the part of the framework that executes chains and agents. |
| Jenkins analogy for LangChain Runtime | LangChain is like Jenkins itself. LangChain Runtime is like the Jenkins build executor that actually runs the pipeline when you click **Build**. |
| Terraform analogy for LangChain Runtime | Writing Terraform code is similar to creating an Agent. Running `terraform apply` is similar to calling `agent.invoke()`. |
| When does LangChain Runtime start? | It starts when `agent.invoke()` (or another execution method) is called. |
| Who understands the user's English question? | The **LLM** understands the user's natural language. |
| Who decides which Tool should be used? | The **LLM** decides which Tool is appropriate based on the user's request and the tool descriptions. |
| Does LangChain decide which Tool to use? | No. LangChain only executes the tool selected by the LLM. |
| Can the LLM execute the Tool itself? | No. The LLM can only request a tool call. The LangChain Runtime performs the execution. |
| Who checks whether the Tool completed successfully? | The LangChain Runtime executes the Python function and receives its return value or exception. The returned result is then passed back to the LLM. |
| What happens if the Tool fails? | The Python function raises an exception or returns an error. LangChain Runtime captures that result and provides it to the LLM so it can decide what to do next. |
| Can an Agent call multiple Tools? | Yes. An Agent may call one Tool, several Tools, or no Tool at all depending on the task. |
| Does the Agent stop after one Tool call? | Not necessarily. The LLM may continue reasoning and request additional Tool calls until it determines that the task is complete. |
| Can the Agent answer without using any Tool? | Yes. If the LLM already knows the answer, it can return a response without requesting any Tool. |
| Why are Agents more powerful than simple prompts? | Agents can combine reasoning with real-world actions, making them capable of solving more complex tasks than a single LLM response. |
| What is the most important idea about Agents? | The **LLM is the Brain** (reasoning). **LangChain Runtime is the Hands** (execution). Together they create an AI Agent capable of interacting with the real world. |

---

# Key Revision Notes

- AI Agent = **LLM + Tools + LangChain Runtime**
- ReAct = **Reason → Act → Observe → Repeat**
- `@tool` exposes Python functions to the LLM.
- `create_agent()` builds the Agent.
- `agent.invoke()` starts execution.
- The LLM **thinks**.
- LangChain Runtime **executes**.
- Tools are normal Python functions.
- The LLM **never executes Python code directly**.
- LangChain Runtime receives tool requests, executes them, returns the results, and keeps the reasoning loop running until the goal is achieved.

> **Golden Rule:**  
> **LLM = Brain** 🧠  
> **LangChain Runtime = Hands** ✋  
> **Tools = Skills** 🛠️  
> **Agent = Brain + Hands + Skills**

# LangChain Learning Notes - Part 3

> **Topic:** LangChain Runtime Internals, Model API, Tool Calling, Tool Registry, Function Execution, Multiple LLM Calls, Complete Agent Lifecycle

| Question | Answer |
|----------|--------|
| What happens internally when `agent.invoke()` is called? | `agent.invoke()` starts the LangChain Runtime. The runtime prepares the prompt, collects available tools, sends the request to the LLM, executes requested tools, and returns the final response. |
| What is the first thing LangChain Runtime does? | It gathers the user message, conversation history (if any), system prompt, available tools, and agent configuration before contacting the LLM. |
| Does `agent.invoke()` directly call the Python function? | No. It first sends the request to the LLM. The Python function is executed only if the LLM requests a tool. |
| What is the Model API? | The Model API is the communication interface between LangChain and the LLM provider. It sends prompts to the model and receives responses. |
| What is the purpose of the Model API? | It allows LangChain to communicate with different LLM providers using HTTP requests or SDKs. |
| Does LangChain communicate directly with the LLM? | No. LangChain communicates through the provider's Model API (for example Ollama API or OpenAI API). |
| What is the Ollama Model API? | It is the local HTTP API exposed by the Ollama server that receives prompts and returns responses from models such as Llama 3.2. |
| What does ChatOllama do internally? | ChatOllama formats LangChain requests into the format expected by the Ollama Model API and converts responses back into LangChain objects. |
| What happens before sending the prompt to the LLM? | LangChain Runtime builds a request containing the user message, system prompt, previous conversation (if any), and tool definitions. |
| What is a Tool Schema? | A Tool Schema is a JSON description of a tool generated automatically by LangChain from the `@tool` decorator, function signature, type hints, and docstring. |
| Why does LangChain generate Tool Schemas? | LLMs cannot understand Python functions directly. Tool Schemas describe the available tools in a format the LLM can understand. |
| What information does a Tool Schema contain? | Tool name, description, parameters, parameter types, and required inputs. |
| How does LangChain build Tool Schemas? | It reads the Python function decorated with `@tool`, extracts its metadata, and converts it into JSON Schema. |
| Does the LLM receive Python code? | No. The LLM receives only the Tool Schema, not the Python implementation. |
| What does the LLM do after receiving Tool Schemas? | It reasons about the user's request and decides whether a tool should be called. |
| Does the LLM execute the Tool? | No. The LLM only returns a Tool Call Request indicating which tool should be executed and what arguments should be used. |
| What is a Tool Call Request? | It is a structured response from the LLM requesting execution of a particular tool with specific arguments. |
| Example of a Tool Call Request | `{ "tool":"restart_pod", "arguments":{"pod_name":"nginx"} }` |
| What is the Tool Registry? | The Tool Registry is an internal mapping maintained by LangChain that associates tool names with their corresponding Python functions. |
| Why is a Tool Registry required? | When the LLM requests a tool by name, LangChain uses the Tool Registry to locate the correct Python function. |
| Does the developer create the Tool Registry manually? | No. LangChain automatically creates and manages the Tool Registry. |
| How does LangChain locate a Tool? | It searches the Tool Registry using the tool name returned by the LLM. |
| Who executes the selected Tool? | LangChain Runtime instructs Python to execute the corresponding function. |
| Who actually runs the Python code? | The Python Interpreter executes the function. LangChain Runtime coordinates the execution. |
| What can happen inside a Tool? | The Tool may call REST APIs, execute shell commands, interact with Kubernetes, query databases, create AWS resources, or perform any Python operation. |
| What happens after the Tool finishes? | The Python function returns a result or raises an exception. LangChain Runtime receives that outcome. |
| Does LangChain immediately return the Tool result to the user? | No. The Tool result is first sent back to the LLM so it can continue reasoning. |
| Why is the Tool result returned to the LLM? | The LLM needs the Tool output to determine whether another Tool is required or whether it can produce the final answer. |
| Can the LLM request another Tool after receiving the first Tool result? | Yes. The LLM may continue reasoning and request additional Tool calls if necessary. |
| What is meant by Multiple LLM Calls? | During one `agent.invoke()` execution, LangChain may call the LLM multiple times as part of the Reason → Act → Observe loop. |
| Why are multiple LLM calls necessary? | Complex tasks often require multiple reasoning steps and multiple Tool executions before reaching the final answer. |
| Example of Multiple LLM Calls | Multiply → Observe Result → Divide → Observe Result → Final Answer. |
| Does every Agent request require multiple Tool calls? | No. Some requests require no Tool calls, some require one, and others require several depending on the task. |
| What happens if a Tool fails? | Python raises an exception or returns an error. LangChain Runtime captures it and provides the information to the LLM for further reasoning. |
| Who checks whether the Tool executed successfully? | Python detects success or failure, while LangChain Runtime receives the result or exception and manages the workflow. |
| Does the LLM understand Linux exit codes? | No. The LLM receives only the structured result or error returned by the Tool. |
| Who creates the final natural language response? | The LLM creates the final human-readable response after processing all Tool outputs. |
| Does Python generate the final explanation? | No. Python only executes functions and returns data. The LLM converts that data into natural language. |
| What object is finally returned by `agent.invoke()`? | LangChain returns an AIMessage or Agent Response object containing the final answer and metadata. |
| What is the Complete Agent Lifecycle? | User Request → LangChain Runtime → Build Prompt → Model API → LLM Reasoning → Tool Request → Tool Registry Lookup → Python Function Execution → Tool Result → LLM Reasoning → Final Response → User. |
| What is the biggest responsibility of LangChain Runtime? | To orchestrate the entire Agent workflow, including prompt construction, model communication, tool execution, conversation management, retries, and final response generation. |
| What is the difference between Thinking and Doing? | The LLM performs the **Thinking (Reasoning)**, while LangChain Runtime and Python perform the **Doing (Execution)**. |
| Jenkins analogy for Agent execution | Jenkins Pipeline decides which stages to execute. The Linux shell executes the commands. Similarly, the LLM decides which Tool to use, while LangChain Runtime and Python execute it. |
| CEO analogy for Agent execution | LLM = CEO (Decision Maker), LangChain Runtime = Manager (Coordinator), Python Functions = Workers (Execution). |

# LangChain Learning Notes - Part 4

> **Topic:** Model Context Protocol (MCP), ChatOllama vs MCP, Model API vs MCP, JSON-RPC 2.0, REST vs JSON-RPC, LangChain + MCP

| Question | Answer |
|----------|--------|
| What is MCP? | MCP (Model Context Protocol) is an open protocol that standardizes how LLM applications communicate with external tools, services, databases and applications. |
| Why was MCP created? | Before MCP, every application had to build custom integrations for every tool or service. MCP provides one standard protocol so any compatible client can communicate with any compatible server. |
| What problem does MCP solve? | It eliminates the need to write separate integrations for every LLM, framework, and external application by providing a common communication standard. |
| What is the full form of MCP? | Model Context Protocol. |
| Is MCP an LLM? | No. MCP is only a communication protocol. It does not generate text or perform reasoning. |
| Is MCP a Python library? | No. It is a protocol specification. Different programming languages provide SDKs to implement MCP Clients and MCP Servers. |
| Is MCP an API? | No. MCP is a protocol that defines how requests and responses should be exchanged between clients and servers. |
| What is an MCP Client? | An MCP Client is an application (such as Claude Desktop, LangChain application, or VS Code extension) that connects to MCP Servers and requests tools or resources. |
| What is an MCP Server? | An MCP Server exposes tools, resources and prompts to MCP Clients using the MCP protocol. |
| What does an MCP Server provide? | Tools, Resources, Prompts and sometimes additional capabilities that can be used by AI applications. |
| Can multiple clients connect to one MCP Server? | Yes. Multiple MCP-compatible clients can communicate with the same MCP Server. |
| Can one client connect to multiple MCP Servers? | Yes. A client can simultaneously connect to many MCP Servers exposing different tools. |
| Is ChatOllama an MCP Server? | No. ChatOllama is only a LangChain adapter used to communicate with the Ollama Model API. |
| Is ChatOllama related to MCP? | No. ChatOllama communicates with an LLM. MCP communicates with external tools and services. They solve different problems. |
| Difference between ChatOllama and MCP? | ChatOllama connects LangChain to an LLM. MCP connects AI applications to external tools and services. |
| Can LangChain work without MCP? | Yes. LangChain can directly execute Python tools without MCP. |
| Why would we use MCP with LangChain? | MCP allows LangChain to use tools running in external MCP Servers instead of only local Python functions. |
| Does LangChain require MCP? | No. MCP is optional. LangChain already supports normal Python tools. |
| What is a Model API? | A Model API is the interface through which LangChain communicates with an LLM provider such as Ollama, OpenAI or Anthropic. |
| What does a Model API do? | It sends prompts to an LLM and receives generated responses. |
| Does a Model API execute tools? | No. It only communicates with the language model. |
| Difference between Model API and MCP? | Model API communicates with the LLM. MCP communicates with external tools, applications and services. |
| Example of a Model API | Ollama API, OpenAI API, Anthropic API, Gemini API. |
| Example of an MCP Server | GitHub MCP Server, Filesystem MCP Server, PostgreSQL MCP Server, Kubernetes MCP Server. |
| Can an LLM communicate directly with an MCP Server? | No. The MCP Client communicates with the MCP Server. The LLM only reasons about which tool should be used. |
| What protocol does MCP use? | MCP commonly uses JSON-RPC 2.0 as its communication protocol. |
| Why does MCP use JSON-RPC instead of REST? | JSON-RPC is lightweight, supports request-response messaging, notifications and bidirectional communication patterns that are useful for AI tool interactions. |
| What is JSON-RPC? | JSON-RPC is a lightweight remote procedure call protocol where methods are invoked by sending JSON messages. |
| What does RPC stand for? | Remote Procedure Call. |
| What is a Remote Procedure Call? | It allows one application to execute a function located in another application as if it were a local function call. |
| Example of JSON-RPC Request | `{ "jsonrpc":"2.0", "method":"restartPod", "params":{"name":"nginx"}, "id":1 }` |
| Example of JSON-RPC Response | `{ "jsonrpc":"2.0", "result":"Success", "id":1 }` |
| What is REST? | REST (Representational State Transfer) is an architectural style for designing HTTP APIs using resources such as `/users`, `/orders`, `/pods`, etc. |
| REST communication style | Uses HTTP methods like GET, POST, PUT, DELETE to manipulate resources. |
| JSON-RPC communication style | Uses a method name and parameters to invoke remote functions. |
| REST example | `POST /pods/restart` |
| JSON-RPC example | `restartPod("nginx")` |
| Which protocol is more procedure-oriented? | JSON-RPC. |
| Which protocol is more resource-oriented? | REST. |
| Is JSON-RPC bidirectional? | Yes. It supports request-response communication and notifications, making it suitable for interactive AI workflows. |
| Why is bidirectional communication useful for AI? | Agents may need multiple back-and-forth interactions with external tools during reasoning. JSON-RPC naturally supports this communication style. |
| Does REST support bidirectional communication? | REST is primarily request-response and is not designed for conversational or tool-calling workflows. |
| Is MCP replacing REST APIs? | No. Existing REST APIs continue to exist. MCP provides a standard interface for AI applications to use tools. |
| Can an MCP Server internally call REST APIs? | Yes. Many MCP Servers internally use REST APIs, databases or SDKs while exposing a standard MCP interface to clients. |
| Can MCP expose existing enterprise applications? | Yes. Organizations can build MCP Servers that expose internal systems such as Jira, Jenkins, Kubernetes or databases. |
| How does LangChain use MCP? | Instead of executing a local Python function, LangChain can communicate with an MCP Client which forwards tool requests to an MCP Server. |
| LangChain + MCP execution flow | User → LangChain Agent → LLM → MCP Client → MCP Server → External Tool → MCP Client → LLM → Final Answer. |
| What is the biggest advantage of MCP? | One standard protocol allows any MCP-compatible AI application to access any MCP-compatible server without writing custom integrations. |
| What is the relationship between LangChain and MCP? | LangChain builds AI applications. MCP standardizes how those applications communicate with external tools. They complement each other rather than compete. |

# Oracle Quiz Questions

| Question | Answer |
|----------|--------|
| What is the primary benefit of LangChain's standardized model interface? | It allows developers to switch LLM providers with minimal code changes. |
| Does LangChain guarantee identical responses across all LLMs? | No. Different LLMs have different capabilities, reasoning quality, context windows, and outputs. |
| Does LangChain automatically fine-tune LLMs? | No. Fine-tuning is performed separately by the model provider or custom training pipelines. |
| Does LangChain remove the need for API keys? | No. Cloud providers still require API keys. Local models like Ollama usually do not. |
| Why does LangChain provide a common model interface? | So developers can change providers (OpenAI, Ollama, Gemini, Claude, etc.) without rewriting the entire application. |
| Why can't an LLM execute a Tool directly? | Because an LLM is a text prediction model. It cannot execute Python code or interact directly with operating systems or APIs. |
| What does the LLM actually do when it needs a Tool? | It generates a Tool Call Request describing which Tool should be executed and with what arguments. |
| Who executes the Tool? | LangChain Runtime coordinates execution and Python executes the actual function. |
| What is the Brain of an Agent? | The LLM. |
| What are the Hands of an Agent? | LangChain Runtime and Python Tools. |
| Can an Agent answer without Tools? | Yes. If the LLM already knows the answer, it can respond directly. |
| Can an Agent use multiple Tools? | Yes. The LLM may request multiple Tool calls before producing the final answer. |

# Common Interview Questions

| Question | Answer |
|----------|--------|
| What is LangChain? | An open-source framework for building LLM-powered applications using reusable components such as Prompts, Models, Memory, Tools, Chains and Agents. |
| Is LangChain an LLM? | No. LangChain is a framework, not a language model. |
| What is ChatOllama? | A LangChain integration that connects LangChain to an Ollama server. |
| What is Ollama? | A local inference server used to run open-source LLMs such as Llama 3.2. |
| What is a PromptTemplate? | A reusable prompt with placeholders that are replaced at runtime. |
| Difference between PromptTemplate and ChatPromptTemplate? | PromptTemplate creates one text prompt. ChatPromptTemplate creates structured conversations using roles like System, Human and AI. |
| What is AIMessage? | The object returned by LangChain after an LLM call. |
| Why do we use `response.content`? | Because the actual generated text is stored inside the `content` field of the AIMessage object. |
| What is LCEL? | LangChain Expression Language used to connect components using the `|` operator. |
| What is a Chain? | A pipeline where the output of one component becomes the input of the next component. |
| What is Memory? | A mechanism for storing previous conversation messages and sending them back to the LLM. |
| What is an AI Agent? | An application that combines an LLM with Tools to solve problems through reasoning and action. |
| What is a Tool? | A Python function exposed to an Agent using the `@tool` decorator. |
| What is `create_agent()`? | Creates an Agent by combining an LLM with a list of Tools. |
| What is `agent.invoke()`? | Starts Agent execution by invoking the LangChain Runtime. |
| What is LangChain Runtime? | The execution engine responsible for orchestrating prompts, LLM calls, Tool execution, retries and final response generation. |
| Difference between LangChain and LangChain Runtime? | LangChain is the framework. LangChain Runtime is the execution engine inside the framework. |
| What is a Tool Registry? | An internal mapping between Tool names and Python functions. |
| What is a Tool Schema? | A JSON description of a Tool automatically generated from the Python function. |
| Who decides which Tool to use? | The LLM. |
| Who executes the Tool? | LangChain Runtime (through Python). |
| Who generates the final answer? | The LLM. |
| What is the Model API? | The communication interface between LangChain and the LLM provider. |
| What is MCP? | A protocol for connecting AI applications with external tools and services. |
| Difference between Model API and MCP? | Model API communicates with LLMs. MCP communicates with external tools. |
| Is ChatOllama MCP? | No. ChatOllama is an adapter for Ollama. MCP is a communication protocol. |

# Golden Rules

1. **LLM thinks, it does not execute code.**
2. **LangChain Runtime orchestrates execution.**
3. **Python executes the Tool.**
4. **The Tool returns data.**
5. **The LLM converts data into natural language.**
6. **Model API talks to the LLM.**
7. **MCP talks to external tools.**
8. **LangChain builds AI applications; MCP standardizes tool communication.**
9. **An Agent = Brain (LLM) + Hands (LangChain Runtime) + Skills (Tools).**
10. **Understanding "who thinks" and "who executes" is the key to mastering LangChain Agents.**
